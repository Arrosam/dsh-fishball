### R3B-07 — P1: embedded controls remain Chinese when host returns to English

1. With the English host and a loaded English Fishball chat, select `中文` in host General settings and close Settings. Host shows `Fishball` / `运行中` / `刷新`; child shows `DSH 目标`, `已连接`, `Fishball 设置`, `DSH 设置`, `对话`, `轨迹`. Host DOM language is `zh-CN`.
2. In the same visible tab, select `English` in host General settings and close Settings. The host shows `Fishball` / `running` / `Refresh`, `Workspaces`, and `Default workspace`, with a `Fishball chat` iframe and host DOM language `en`.
3. **Actual:** The usable embedded page still shows `收起侧边栏` (Collapse sidebar), `全局面板` (Global panels), `插件` (Plugins), `DSH 目标` (DSH targets), `已连接` (Connected), `设置` (Settings), `Fishball 设置` (Fishball settings), `DSH 设置` (DSH settings), `更多操作` (More actions), `打开右侧边栏` (Open right sidebar), `对话` (Chat), `轨迹` (Trajectory), and `轮次导航` (Turn navigation). The mismatch persisted through a later settings open/close and another observation. No error banner, raw authentication sentence, or stuck checking screen appeared. Console: no messages captured on the locale test tab. The child DOM `lang` was not directly read; the host `lang` values above were directly read.
4. **Expected:** the embedded controls return to English as the host does. This is a localization failure on the normal language-switch flow, not a P0 loss of chat. Investigate the host's `frameLangStore` and the child's `applyLanguage` as separate checkpoints; the cause was not verified.

### Cleanup and limitations

Both owned browser sessions stopped successfully. Only the disposable target was removed. The temporary name, initial Fishball logo choice, host appearance (`System`) and host locale (`English`) were restored; the final embedded locale remained Chinese as reported. The finished `R3B Workspace Check` worker was left under Default workspace as evidence. No second connected target, frame recovery, pending badge, status-warning Refresh, or panel-overflow fixture was forced. BrowserSkill guard failures were reported in the session; they were not counted as application defects. The target settings tab console had a verbose DOM warning (`[DOM] Password field is not contained in a form: (More info: [link omitted]) %o`), not a console error.
