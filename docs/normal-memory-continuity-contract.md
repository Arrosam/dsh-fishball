## 2. CAS, revision, import and deletion meanings

Each edit uses the existing encrypted workspace projection transaction and exact namespace revision. correct/forget also require exact fact revision and a live matching fact; correction cannot change its kind or allocate a replacement identity. Correct increments fact revision, records previousRevision and new sources/time/confidence/content, removes the prior value from the live core. Forget increments revision, removes current core content and retains the fact's provenance/deleted marker. IDs remain monotonically allocated and never reused after deletion/reopen. Opposite separately entered facts remain candidates requiring verification, not silent winner selection.

Existing correct stores the preceding revision **number**, not historical old-body snapshots or a complete edit journal. Previous immutable contexts/artifacts/exports may still contain earlier content. Current core retrieval has no persistent cache and reads authenticated current namespace each time; neither old value nor fact tombstone participates in new retrieval. Client caches are sealed/cleared after successful mutation, disconnect/config change and unload. Previously prepared contexts fail exact expectedMemory revision at later commit/execution; mutation never rewrites their encrypted bytes or an admitted action digest. An already admitted effect is not rolled back. The installed worker composer receives the actual successful memory mutation receipt and invalidates its process-private prepared-input/preview origin; it never automatically prepares or grants replacement context.

MemoryAdapter computes a complete canonical operation/request digest and looks up signed memoryCommandReceipt before deriving/writing a projection. Identical historical input returns its original immutable receipt with deduplicated:true, even after newer revisions/deletion; changed input or cross-operation command reuse conflicts. Receipt revision is a historical acknowledgement, not current state and not permission to resurrect data. Client explicitly refreshes current memoryStatus/read after mutation or uncertain result. Two processes racing the same namespace/fact CAS admit at most one edit; async parse/read/assembly uses detached input and rechecks namespace/lifetime before commit. A thrown/nonmatching persistence receipt reports stable uncertainty rather than saved state.

Pinned import accepts only explicit strings in existing main snapshot/release turns.jsonl format, using the existing pinned parser and current private destination scope. Native df.memory-projection/v1 or df.fishball-memory/v1 exports are **not** automatically accepted as that legacy raw import format; their scope/metadata cannot be stripped silently. Source snapshot keys and turn rows retain current closed parser vocabulary; release last-revision-wins by turn ID and snapshot/log union are shown before consent. Duplicate cross-kind IDs, truncated/blank malformed rows, future/unknown fields, secrets and overflow refuse the complete import. At most 49152 combined UTF-8 document bytes and at most 65536 serialized request/preview-response bytes in this normal interface; existing parser/record/namespace limits also apply. A normalized preview that cannot be fully displayed within the response bound refuses; do not silently truncate consent or bypass body limits to reach the factory's 4MiB capacity.

Import writes only into a genuinely absent namespace with expectedRevision0, empty projection/idSeq and no tombstone. Parsed records become revision1 facts with the selected sourceRefs/confidence; actual source record timestamps remain recordedAt/at where present. Import-time observedAt is request provenance, not a replacement for every historical record date. The input documents are not authority to resume imported session/inFlight flags, approve actions, import credentials or modify task/worker state. Existing source-default TTLs and normalized Float32 embeddings are disclosed without calling a model. An empty/no-fact import preview refuses rather than creating a revision1 empty namespace under a misleading success label. Reopen preserves the same scope/IDs/projection and original duplicate receipt.

Namespace deletion uses existing authenticated empty-ciphertext tombstone and increments namespace revision; subsequent put/import/remember/prepare cannot resurrect it. Because the normal NI1 namespace is fixed by identity/profile, disable/re-enable/restart does **not** create a fresh one. Deletion means memory is unavailable for this namespace, including memory-enabled context preparation; memoryStatus displays deleted. A future reset/new-namespace operation would need separately frozen identity/retention semantics and is not smuggled into deletion or import. This consequence is displayed before confirmation.

Local deletion removes live namespace ciphertext/current fact bodies only within its confirmed scope. It cannot claim secure physical media erasure, deletion of immutable task contexts/native plaintext logs, old exports/backup copies or third-party copies. Task deletion/export/rescheduling remain authoritative ledger operations under BUB003, not side effects of memory deletion. Owner retention/privacy choices remain section6; absent choices never trigger automated cleanup.

## 3. Source-derived durable conflict check

Actual ContextAssembler excludes a structurally valid selected summary if sourceTaskVersion or sourceAuthEpoch differs from current task facts, returning `{recordRef,reason:'stale_summary',winningTaskVersion}`. The latest protected goal/constraints/admitted supplemental instructions and authoritative work facts win. It validates summary sourceScope/sourceRefs/generatedAt and refuses foreign/future/unavailable malformed material. Existing MemoryAdapter.prepareExecutionContext preserves sourced context but drops conflicts from its persisted envelope/receipt. This unit closes that concrete durable-check gap; it does not claim semantic contradiction detection from arbitrary natural language or confidence scores.

Keep df.execution-context/v1 byte/field/validation/dataDigest meaning unchanged, including sourceScope/source versions/generatedAt/sourceProvenance/memory/ledger snapshot/whole content/counts/retained+dropped refs. Do **not** append conflicts to it or reinterpret summary approval/completion as ledger authority. Add a separately signed `prepared_context_check` association and source-derived checks atomically with the exact successful context write. Record an empty check set too: missing association differs from an authentic zero-conflict evaluation. Old pre-association contexts remain readable historical contexts but cannot falsely acquire an already-performed durable check or normal provenance.

Candidate `df.prepared-context-check/v1` closed signed payload:

```text
{contractVersion,checkRef,taskRef,contextRecordRef,contextDigest,
 sourceTaskVersion,sourceAuthEpoch,committedTaskVersion,committedAuthEpoch,
 semanticRevision,generatedAt,ledgerSnapshotDigest,
 memory:{namespaceRef,revision},method:'version-currentness/v1',
 winningSources:[{recordRef,digest,kind}],
 summaryChecks:[{recordRef,digest,sourceTaskVersion,sourceAuthEpoch,
   generatedAt,sourceRefs,disposition}],
 conflicts:[{recordRef,reason:'stale_summary',winningTaskVersion,
   winningAuthEpoch}]}
```

Refs/digests are hex64; dates/CAS/revisions are bounded safe integers. winningSources are exact latest goal, constraints if present and protected admitted current instructions (kinds goal/constraints/current_instruction), never caller-selected winner text. summaryChecks enumerates only the exact actually examined/selected valid same-scope summaries; disposition is retained_background/dropped_for_budget/excluded_stale_summary. A summary that was not selected/examined is not claimed checked. Checks derive whole original authenticated summary digest/scope/version/time/source refs; conflict entries are the exact subset whose versions differ. At most 64 examined summaries and winner sources, 16 sourceRefs per summary, distinct IDs and deterministic ordering; original context/record limits may make a smaller actual set necessary. A check association that exceeds the existing selected metadata limit refuses before any context commit; do not silently raise 4096 or truncate the list. No summary/user prose appears in signed metadata or diagnostics.

This is **version/currentness checking**, not natural-language conflict adjudication. Same-version semantically contrary text cannot be labelled detected by this method. Owner current instructions always stay protected; memory conflictRefs/retrieval requiresVerification remain non-authoritative check prompts. Explicit semantic conflict resolution, broader summary generation thresholds and useful model behavior need their separately scoped source oracles; an empty association is not evidence of those capabilities.

It never performs asynchronous source/tokenizer/model/native calls or recursively invokes public store transactions while under the ledger lock. No automatic new summary, context rewrite/check backfill, preparation, grant/resume or source query.
