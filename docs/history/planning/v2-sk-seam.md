# SK-SEAM — private Skills feasibility on both installed SDKs

## 1. Decision and scope

**Result: the public catalog, native loading, manager-scope registration and explicit invalidation seams exist on both SDKs. A dedicated trusted host operation can write while ordinary agent tools remain read-only. This is not an SDK-provided confined-storage exception, and the current composition does not yet satisfy S1–S8.** In particular, stock skill discovery follows symlinks; read-only is not a worker read ACL; and invalidation does not synchronously refresh every UI or already-injected instruction. Do not mark the complete SK implementation or its acceptance gate passed from this investigation.

Investigated baseline: `cd87106f3bc761d68c6e919e83ffd40ac8e86262`, branch `docs/v2-final-scope`. Report branch: `docs/v2-sk-seam`, created at that exact commit. Only this report is delivered. The assignment is [SK-SEAM:157–158](<v2-final-scope.md#L157-L158>), not SK implementation, T-SK test authoring, deployment, or browser verification.

Policy remains settled: private child-home native skills; only Fishball directly loads/manages them; workers receive needed instruction bodies in messages; autonomous dedicated list/read/create/update/remove/reload; all ordinary file/shell writes remain read-only; strict name/root/format validation, atomic publication and truthful refresh failures. See [final scope:76–83](<v2-final-scope.md#L76-L83>) and [S1–S8:248–261](</Volumes/SSD1/GitHub/dsh-fishball/.agents/worktrees/design-core-requirements/docs/test-design/core-requirements.md#L248-L261>). ## 2. Discovery: what selects the library

### 2.1 Homes, profile composition and roots

The installed SDK directory is **not** the skill home. Home resolution accepts explicit configuration, then `DSH_HOME` / `DSH_AGENTS_HOME`, then the user's default `.dsh` / `.agents` directories. It normalizes paths; it is not an ownership or confinement check (E1). Profiles compose the registry/provider plugins; filesystem lookup uses those provider settings and the lookup's cwd, rather than automatically treating a profile directory as the only skill root.

The native filesystem provider supports these roots (E2–E3):

1. With defaults enabled and cwd supplied, nearest `.git` project root (or original cwd if none): `.dsh/skills`, then `.agents/skills`.
2. Explicit `customSkillDirs`.
3. With defaults enabled, resolved DSH-home `skills`, then agents-home `skills`.
4. An explicitly configured bundled root; environment `DSH_BUNDLED_SKILL_DIR` is used only when defaults are enabled.

Discovery is one root level: each directory contributes its immediate `SKILL.md`, and an immediate flat Markdown file may also contribute. It does not recursively search the whole home (E4). The registry combines all visible providers, with global/ancestor layers inherited and nearer layers overriding **same names**, not excluding other names (E5). Within one layer candidate rank/order determines duplicate precedence.

**Private-only composition:** construct—not spread—provider config with `includeDefaultRoots: false`, exactly `customSkillDirs: [ownedChildSkillsRoot]`, no `bundledSkillDir`, and no other global/preset skill providers or runtime contributions that would import main/project/bundled skills. `watchFollowSymlinks: false` can limit watching but cannot secure reads. Merely changing HOME or `dshHome` does not disable project/custom/bundled roots. Never register the private library in main DSH, copy/synchronize main skills, or retry a failed child lookup in main-home skills.

- [Private layout:46–62](<../../packages/instance/src/native-runtime/files.js#L46-L62>) places child DSH home beneath main home at `fishball/runtime/dsh-home`. ## 3. Native catalog, load and visibility timing

### 3.1 Public contract and lifecycle

`agentCtx.skills.registerProvider(create)` supplies `SkillProviderControl { signal, invalidate }`; its disposer owns that registration. A provider implements `list(options)` and `get(candidate, options)`. `invalidate()` is synchronous cache invalidation/notification, **not** an async “reload complete” operation. No public global `skills.reload()` is needed or established here (E6–E8).

The public readback API is `snapshot({ cwd, scope: manager, signal })` with completeness, and `get(name, options)` for a fresh body; `list()` alone returns summaries without completeness ([rc.5 declarations:266–284](</Users/samuel/Library/Application Support/DSH/data/versions/0.2.1-rc.5/node_modules/@deepseek-ai/dsh-skill/lib/types/index.d.ts#L266-L284>), [rc.1 declarations:266–284](</Users/samuel/Library/Application Support/DSH/data/versions/0.2.2-rc.1/node_modules/@deepseek-ai/dsh-skill/lib/types/index.d.ts#L266-L284>)). Keep the registration-specific control in the owned service; release it on disposal. Register through the manager's setup context, never by monkey-patching registry internals. The public `FileSystemSkillProvider` constructor/list/get/dispose can be reused; its standalone YAML/file parser is **not exported** (E9). A public custom provider is also supported, but native parser compatibility would then be Fishball's responsibility.

Provider lookup options publicly contain only cwd/signal. Registry view options additionally contain the viewing scope. Although this implementation forwards the borrowed object, **do not authorize a provider from undocumented `options.scope` access** (E6). Scope-based visibility belongs at registration; receiving-agent authorization belongs at the tool/service boundary.

### 3.2 Exact refresh semantics

| Event | What subsequent consumers can observe | What is not guaranteed |
|---|---|---|
| Initial agent pre-step | Native tool plugin snapshots visible skills, filters model-invocable entries and injects catalog summaries. | Startup-only snapshot or eager model turn merely to prepare a catalog. |
| Existing skill body replaced, same name | Native provider `get` rereads the selected file. A later load can see new body even if candidate metadata is cached. | Already-loaded body is not rewritten; metadata/name additions still require discovery invalidation. |
| Create/delete/metadata change | Call the retained `control.invalidate()` after commit; the next registry lookup collects a fresh candidate catalog. | Cache expiry or a watcher event is not an immediate-publication contract. |
| Next admitted model step after invalidation | Native pre-step compares catalog digest/history and injects a changed catalog; no restart is intrinsically required. | No wake/turn is scheduled by invalidation; an in-flight model request keeps its existing inputs. Body-only changes need not change the summary digest. |
| Explicit reload | Fishball invalidates and awaits a fresh manager-scoped snapshot, checks `complete`, and verifies any required committed target via `get`. | Invalidation's `void` return and caught observer errors do not prove reload, list or UI success. |
| Previously loaded body / worker instructions | Remain in committed conversation/history until ordinary context handling changes them. | Reload cannot retract or erase text already delivered. |

Evidence: cache key includes cwd, scope chain and revision; `get` delegates after candidate selection (E5/E7). Invalidation increments revision, clears completed caches and emits `skills/change`; observer failures are contained rather than load-bearing (E8). Native pre-step and tool body loading are E10; digest inputs and the loop's per-step hook are E24. The filesystem provider's `fs/observed` hook recognizes first-party write/edit actors; dedicated host storage mutations must explicitly invalidate and must not impersonate those tools (E11).

**Version difference:** rc.5 does not publish an incomplete pre-step catalog; rc.1 publishes a partial replacement with an explicit warning and retries on future discovery. rc.1 also contains filesystem discovery failures per root; rc.5 can lose the provider's entire observation on a root failure. Neither supports treating an incomplete lookup as successful reload. See E12. Following a committed mutation, return an honest `committed, refresh failed/incomplete` outcome if confirmation fails; do not roll back silently, duplicate creation on retry, or call partial discovery authoritative.

**Native UI limitation:** direct fresh `skills/list` calls and model pre-step refresh are not the already-mounted slash-menu cache. The client caches per-session results and invalidates on preset selection, plugin-manager change and connection reset, not `skills/change` (E13). This investigation establishes no public force-refresh method for that cache. Likewise, a cold `skills/list` resolves a standing preset, not a live manager's exact-scope provider, and can fall back to the global layer if preset resolution fails (E14). Do not solve either limitation by globally mounting private skills, triggering fake plugin changes or restarting the child on every write. Recommend the six operations use live manager-scoped service calls; if immediate cold/live slash-menu update is an acceptance requirement, hold that UI seam for a supported extension rather than claiming it works.

## 4. Manager ownership and worker boundary

### 4.1 What the native scope chain proves

An agent has its own scope; native workers compose directly from the same preset generation rather than making their manager's exact agent scope their parent. Therefore a provider registered **only through manager setup** is visible to the manager's native skill consumer but not ordinary native sibling worker compositions. A provider registered in the standing preset would be shared. E15 traces agent scope creation, worker composition and preset binding for both versions.

The native consumer passes the live agent to registry lookup (E10), and exact `scopeOf(agentCtx)` is public (E15). Before exposing capabilities, require setup scope identity to match the actual singleton manager. Register all six dedicated operations there and check the trusted receiving agent is that same live manager (including nested dispatch). Names, role strings or model-supplied booleans are not identity. Dispose registrations on manager/plugin teardown; re-establish them on resume/new generation. Different/custom worker composition must be inspected: a scope explicitly parented to the manager would inherit its contributions. Do not rely only on a provider name or tool hiding.

### 4.2 What it does not prove

S2 is stronger than hiding the native skill catalog. Both filesystem sandboxes allow reads in every mode; a worker retaining general file reads, grep/search, arbitrary shell/evaluate or another host reader can directly read the private library. No general `fs/access` or read-intent veto appears in the inspected filesystem event contract (E16). The read-only shell is not a read-denial sandbox. `chmod 0700` does not distinguish same-user manager and workers.

Thus **current generic worker capabilities do not establish “workers get explicit content only.”** Required future work is an inventory and enforcement of every worker read-capable route: confined providers/receiving-agent guards for ordinary readers, and removal or a separately proven read-confined backend for arbitrary-reading executors. A synchronous tool guard cannot asynchronously canonicalize every alias or safely parse arbitrary shell commands. Do not claim a skill-tool guard alone closes this gap. Native forked history can also carry already-injected content; catalog isolation does not erase that content and the intended explicit delegation boundary must be verified.

If preserving arbitrary worker local reads is mandatory, strict direct-read exclusion cannot be claimed with these SDK defaults. A stronger OS read boundary would require a separately supported design. This is a concrete capability limitation, not reopening S2 or silently downgrading it to a prompt instruction.

## 5. Dedicated writes while generic tools remain read-only

### 5.1 Actual public/storage rules

Neither examined SDK declares a special `storage-write` root-registration API in the inspected skill, filesystem/sandbox and storage contracts. The decisive positive behavior is that `read-only` rejects filesystem mutations **before** evaluating writable roots (E17). rc.1's additional writable roots apply only in workspace-write; rc.5 lacks that option in the examined helper (E18). Neither supplies the required narrow exception.

Trusted Host plugin JavaScript executes in the host process; the tool executor calls its registered body, not an OS/file sandbox wrapper around arbitrary JavaScript (E19). Host storage backends themselves use direct Node storage, independently of model `ctx.fs` policy (E20). This supports a dedicated **trusted Fishball storage service**, invoked only by a manager-only operation, with no per-write approval request. It does not automatically authorize arbitrary paths or prove confinement. Fishball owns that validation and capability boundary. Extensible pre-execute policies can independently deny or ask; the shipped Fishball composition must avoid adding approval/diff-review hooks to these dedicated operations. The claim is absence of an implicit generic-write approval wrapper, not immunity from every deployment's plugins.

The public storage-domain/JSON backend is not a native skill writer: default host composition stores it under resolved DSH-home `storages`, using its own table/file format, not the required native library layout (E20). Do not reinterpret its configurable root as an SDK permission grant, or store a second authoritative JSON copy and quietly materialize Markdown later.

Keep ordinary write/edit/delete/move/shell tools on their existing sandboxed providers in read-only. Do not swap the manager's generic `ctx.fs` for an unsandboxed provider, set temporary full access, add ordinary writable roots, request escalation, or route authoring through shell. Public guard/restriction mechanisms can only narrow tool access; they are appropriate for denying non-manager callers, not broadening the filesystem (E19/E21). The dedicated operation must never accept a pathname, command, executable, arbitrary asset, alternate root or “write any content anywhere” request.

### 5.2 Confinement and publication obligations

The fixed root is `<actual owned child DSH home>/skills`; inputs select a skill **name**, not a path. Explicit child configuration must supply the home: a parent-host call to a default home helper would resolve the parent home, not magically select the child (E1). Required stored layout is `<root>/<name>/SKILL.md`.

The future implementation must establish these properties; the SDK does not provide them as a combined primitive:

1. **Validate before any path use.** Exact kebab-case grammar `^[a-z0-9]+(?:-[a-z0-9]+)*$`; reject absolute/traversal/root/empty/separator/alias/sibling-prefix input. Anchor the real owned child root; validate existing ancestors, skill directory and file identities/types for list/read/load and mutation. Never recursively remove the library root or foreign/ancillary subtrees. A prefix string check is not containment.
2. **Reject escaping links before reads, not after candidate discovery.** Native discovery parses each candidate while listing and follows symlinks through `stat`, `realpath` or `ctx.fs` (E4/E22). Filtering candidates after native `list()` has already allowed the read. Watcher settings are not security settings. Handle hardlinks too: realpath cannot detect a foreign inode hardlinked into the library; replacing via rename avoids mutating that referent, but reading it can still leak foreign content.
3. **Constrain the native reader itself if reusing it.** Candidate design: a private provider-owned Cordis context with a confined read filesystem service, then the public `FileSystemSkillProvider`, defaults disabled, sole custom root, no bundled root and preferably no host watcher dependence. All resolve/listDir/stat/readText paths (and returned `processPath`/candidate locators) must stay confined with no fallback to the Node reader. Set `watch: false` for this candidate so host watchers do not add an unchecked filesystem path; explicit owned invalidation supplies refresh. A separate provider context must not replace the manager's ordinary filesystem. E22 proves native delegation, not the complete correctness of this new scoped adapter. Its service scoping, cancellation, identity/race behavior and refusal paths remain implementation gates.
4. **Validate full native documents before commit.** UTF-8, YAML frontmatter delimited by `---`, nonempty name/description, directory/name match, valid grammar, `disable-model-invocation` absent/false. Native parsing accepts more shapes/policies than S5/S6; Fishball must enforce the settled narrower contract, not assume native discovery enforces directory/name equality. No auxiliary executor/writer. No new scanner/approval gate is inferred.
5. **Serialize validation/commit/reload for cooperating operations.** Create must not overwrite; update must target the selected valid skill; remove must remove only the known skill. Publish a complete old/new document atomically, not an in-place partial write. The public atomic-write helper uses exclusive same-directory temp files and rename, but follows parent components, can create directories, and does not itself enforce create-only semantics, root ownership, skill validation or catalog invalidation (E23). Its documented atomicity excludes fsync crash durability; do not silently promise power-loss durability.
6. **Truthful outcomes and convergence.** Before commit: refusal/cancellation/failure leaves prior state. After commit: preserve the new state and explicitly report refresh failure, with subsequent list/read/reload able to reconcile it. Record or reconstruct committed state even if tool delivery is cancelled; the generic pipeline may label a late successful body aborted (E19). Do not claim rollback when only result delivery failed. Serialize/revalidate against concurrent create/update/remove and verify exact native load after refresh.

**Race/threat-model limit:** both SDK sandbox implementations explicitly accept a residual ancestor-symlink-swap TOCTOU in trusted-code path containment (E17). `lstat`/realpath checks plus no-follow final opens narrow the race but do not prove race-free ancestor traversal. The existing [private-file helpers:7–42](<../../packages/instance/src/native-runtime/files.js#L7-L42>) provide useful ownership/exclusive-open patterns, not a complete native skill-root I/O solution. For S5 under cooperating trusted host processes, implement and test anchored ownership, no-follow/handle checks and serialization; do not describe it as protection against arbitrary same-UID hostile replacement. If that stronger guarantee is required, hold the seam for an OS/handle-relative solution rather than making a generic permission fallback.

## 6. Alternatives, tradeoffs and recommendation

| Option | Benefit | Limitation / disposition |
|---|---|---|
| **Dedicated manager operations + trusted confined host service + guarded native filesystem provider** | Public provider/control APIs, native parser and native consumer retained; ordinary read-only unchanged; explicit commit/invalidation. | **Recommended design direction, not proven implementation.** Needs confined read-service composition, all-path ownership checks, atomic semantics and worker-read closure. |
| Custom `SkillProvider` + same confined host service | Full control of candidate discovery/read surface; no stock scanner reading outside before filtering. | Public seam exists, but no exported standalone native parser; must demonstrate native-format compatibility and avoid unsupported private imports/copied parser internals. Use only if guarded native reuse is not viable. |
| Stock private-root provider alone, or post-filtering its candidates | Minimal code and native format. | Reject as complete solution: symlink-following reads occur during discovery; four existing roots/retained bundled config and generic workers remain leaks. |
| Standing-preset/global provider | Cold UI can discover it easily. | Reject: shares private skills with other agents; exact-scope manager ownership lost. |
| Runtime `skills.register` definitions | Public API for in-memory skill contributions. | Does not itself supply durable native files, their lifecycle or rereads; risks two authoritative stores. Not the storage/reload solution. |
| Public storage-domain/JSON tables | Reuses host-owned schema/lifecycle/storage mechanics. | Wrong required layout/format; materialization introduces consistency work. Not a direct S5/S6 solution. |
| Additional roots, sandbox override, local generic filesystem, approval retry | Existing broad mechanisms, superficially easy. | Reject: does not work under read-only as a narrow root exception or violates S3/S4. Never fall back to main-home storage. |
| Watchers/restart/reconnect for reload | Eventually may cause rediscovery/client cache reset. | No deterministic immediate list/load acknowledgement; expensive/disruptive and not rollback. Use explicit invalidation/readback; UI limitation remains explicit. |
| Separate OS read isolation | Could strengthen worker/race boundary. | Not supplied by the skill API; changes deployment/tool access and requires separately supported design. Do not improvise it or reduce S2 to advice. |

**Recommended disposition:** accept the public registration/loading/invalidation seams as statically established on both versions; retain a **conditional SK engineering gate** for confinement and worker access. Proceed to independent requirements-first T-SK design, not implementation acceptance. Keep the owned provider and all six operations in exact manager setup; remove all other roots/providers from that child composition; retain generic read-only. First prove a confined native-reader adapter using the public class, or explicitly select the custom-provider alternative with a compatibility proof. No DSH patch is required for the demonstrated API composition; no claim is made that all remaining safety/UI obligations have already been met without one.
