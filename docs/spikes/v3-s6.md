# Spike V3-S6: `fishball-core` as a plain bundle with its `fishball-ui` guards

Date 2026-11-11. Branch `spike/v3-s6` from `dca935d` (test cases), checked against the design at
`e1e5577` (`design/v3`; that commit only drops `v3-tasks.md` relative to `dca935d`, the design and
requirements text are the same). Investigation only: no product module was changed. Prototype code
is in [`spikes/v3-s6/`](<../../spikes/v3-s6/>) and the raw evidence is in
[`spikes/v3-s6/results/`](<../../spikes/v3-s6/results/>).

**Result: PARTIAL.** The bundle mechanics, the single `dsh.client`, the hosted launch configuration
and the public-API override detection all **pass** on both SDKs, with no host patch. Two things fail
as the design is written, and they force design changes:
1. **`fishball-instance` is not disabled** by core's guard when core is placed *before* the instance
   in `dsh.profile.bundles` (the standalone default of DSH's native install, and the order in the
   design's placement sentence). That is **UIM-DT-01 row 10b**. Bundle patches apply in bundle order,
   and a patch that names a row not inserted yet is silently skipped.
2. **The guards cannot be written as the design lists them.** The session-creating *preset tools*
   are rows inside an agent preset's `config.plugins` list, which no patch can address by id. Core
   has to replace the shipped presets with its own. That in turn makes a **V2 child's existing
   Fishball session unresumable** through DSH's session controller after migration (PLAT-UC-05).

**Round 2 (2026-11-12, §7): PASS.** The user decided Q-S6-1 = B (core reorders itself) and
Q-S6-2 = B, amended: every shipped preset is **switched off, not deleted**; core contributes
`fishball`; fishball-watchdog contributes `watchdog`; there is no migration, and earlier sessions are
discarded. All three items pass on both SDKs. Core's reorder takes effect at the **next start**,
which is one restart: on a standalone DSH (HMR on) the restart is not needed, because DSH recomposes
live; on a hosted child (HMR off) it is. UIM-DT-01 row 10b and PLAT-UC-05 are freed. §1–§6 below are
round 1, kept as run.

## 1. The question

From design §11 V3-S6 and §5a.2 "Engineering check":
- **Q-a.** Can one plain bundle insert its own rows, disable other bundles' rows and set the
  read-only preset, in an ordinary DSH, on both SDKs, without the compatibility preflight or the
  plugin manager reporting a conflict?
- **Q-b.** Can one `dsh.client` serve the page, the recommended tab and the slim settings?
- **Q-c.** Does a hosted child, with the instance's §6.2 launch configuration as overlays, behave
  the same way?
- **Q-d.** Which **public** API gives core the effective composition and policy, so it can report
  `guards-overridden` without reading DSH's files, in both modes?
- **Q-e.** Does the A-lite page work without the instance (standalone)?

The gated sections are §5a.1–§5a.3, §6.2, §8.1–§8.2 and §9.2 (the bundle-patch and composition-order
rows). The requirements they serve are R-FB-01, R-FB-02, R-FB-09, R-FB-10, R-HOST-01, R-ARCH-01,
R-ARCH-02, R-ARCH-06, R-BND-01/02/05, R-MIG-01/02 and R-COMPAT-01.

### 3.2 The preset tools cannot be disabled by id — design change

§5a.2 says core disables "the session-creating preset tools" (V2 `LITE.disabledPresetPlugins`:
`tool-subagent`, `tool-subagent-fork`, `workflow-ptc`, `tool-workflow`, `tool-subagent-control`,
`tool-subagent-list-agents`, `tool-schedule`). In both SDKs these model-facing rows live **inside**
each `@deepseek-ai/dsh-agent-preset` row's `config.plugins` array (`dsh-web-app/presets/*.patch.yml`).
They are not loader groups, so `applyEntryPatches`'s id index does not reach them. The root rows
with the same ids are host-plane rows that `dsh-web-app` already disables. V2 could reach the nested
ones only because the instance rewrote each preset's whole `config` in code at launch time
(`overlay.js` `isolatePlugins`). A static bundle patch cannot do that, because a patch's `config`
**replaces** the whole config.

What the fixture does instead, and what works on both SDKs:
- disable the four shipped presets (`preset-standard`, `preset-ptc`, `preset-cordis`, `preset-minimal`);
- insert its own `preset-fishball` (persona + read-only `tool-fs`), and set
  `agent-preset-registry.default: fishball`.

Result: `agentPresets.list()` = `[fishball]` only. A new session runs preset `fishball`, and the
model is given exactly `read`, `read_image` and `working_directory`, with no subagent, workflow,
schedule or message tool (`modelTools`, `sessionCreatingTools: []`).

The tool set of the real manager is not decided by this; that is core's own preset content (X12
bridge façade and so on). What S6 settles is the **mechanism**: core owns the preset, and does not
patch the shipped ones.

**Migration consequence (scenario F, PLAT-UC-05).** A session created before core was placed records
`agentPreset: standard`. After core is placed:
- with the fixture's design (shipped presets off, new `fishball` preset), `sessionController.agents.resolveAgent`
  fails with **`gateway/internal`** on both SDKs (the cause is not exposed in the result). The page path would show the session as broken.
  `ctx.agents.resume` without a preset (the V2 manager's path) opens it. On rc.1 the model gets
  only `working_directory`; on rc.5 the model is not even called within 15 s. In both cases the
  session keeps its recorded `workspace-write` sandbox and permission `custom`, so the read-only
  preset does **not** apply to an existing session;
- with the variant that **redefines** the shipped id (`preset-standard`'s whole config replaced by
  Fishball's list, default `standard`; the spike's `fishball` preset was left in, so the list is
  `[fishball, standard]`), the controller resumes it on both SDKs and the model gets
  `read`, `read_image`, `working_directory`. The sandbox and permission are still the recorded
  `workspace-write` / `custom`.

So, on top of the preset, core has to re-pin an existing manager session's own policy. V2 already
does it at create time (`chat.js` `configure`: `setSandboxMode` / `setApprovalPolicy`); for a
migrated session it also has to happen at resume.

### 3.5 Q-d: a public API for the effective composition and policy — PASS

Core can compute `guards-overridden` from live services only, with no DSH file read. The probe is
[`guards.js`](<../../spikes/v3-s6/fixtures/fishball-core/guards.js>):

| Fact | Public API (both SDKs) |
| --- | --- |
| Row on/off | `ctx.loader.entries()` → `entry.options.id`, `entry.disabled` (Cordis `Entry`, typed in `cordis-plugin-loader/lib/types/config/entry.d.ts`; `disabled` includes `!!js` expressions and disabled ancestors). The same view is the Remote `pluginInventory.list()` / `readPluginInventory(ctx)` (`dsh-host-plugin-inventory`) |
| Sandbox default | `ctx.sandboxPolicy.defaultMode` |
| Approval default | `ctx.approval.config.policy` (see §6 Q-S6-3) |
| Preset table and default | `ctx.permissionPresets.names`, `ctx.permissionPresets.defaultPreset` (the latter follows the user's settings value) |
| Agent preset default | `ctx.agentPresets.defaultId`; per session `ctx.sessionController.create(...).agentPreset` |
| Per-session truth | `ctx.sandboxPolicy.resolve({ session }).mode`, `ctx.permissionPresets.current(session)` |

**When to check.** On a live change, at least one of the design's triggers fires: the native
Plugins switch raises `plugin-manager/changed` (B1), and a hand edit of the profile patch raises
`settings/document-updated` (B2, B3). Neither needs a restart: the report changed within 1.5 s and
cleared on restore (B3). At start, `appReady.onReady` gives the final state (B4: the reboot
reported `policy.defaultPreset` and `policy.presets`). `settings/document-updated` also fires many
times **during** boot with partial state: before `appReady` the probe saw `policy.sandbox` as
overridden for a while. Core must ignore checks before app ready (the design's "at app ready, and on
every `settings/document-updated`" is right; the report must not be published earlier).
`settings/document-updated` alone does **not** cover B1; `plugin-manager/changed` must be added to
the trigger list.

The plugin manager also has a static view: `listBundles()` → `overrides` names every row a bundle
patches. Core could use it for "what I tried to change", but not for "what is in effect", so the
loader view stays the source of truth.

## 6. Design changes this spike forces

### Q-S6-1. In which order must core's patch apply, and how is that guaranteed?

**Decided 2026-11-12: B** (core reorders itself, hosted and standalone). Proven in §7.1.

**Background.** DSH applies bundle patches in `dsh.profile.bundles` order. An id patch on a row
that is not inserted yet is skipped, and the only trace is a debug-level loader warning. DSH's native
install appends in install order. So in standalone mode, core is first whenever the user installs it
first, the natural reading of §5a.3, which lists core first. Its guard on `fishball-instance` (UIM-DT-01 10b) then
has no effect, and the same holds for any guarded row of a bundle installed after core. In hosted mode the instance controls the order.

**Options.**
- **A.** Hosted: the instance places core last. Standalone: core detects a guard row that it could
  not apply (the row is present and enabled though core's patch disables it) and reports it as
  `guards-overridden` with a reason such as `order`. The README tells the user to move core last.
  This needs no new mechanism, and it is consistent with Q20 (report, never re-apply).
- **B.** As A, but core itself reorders `dsh.profile.bundles` through the plugin manager (deselect
  and select itself) at first start, then asks for a restart. This changes another component's state
  at runtime, which the design so far avoids.
- **C.** Drop the `fishball-instance` guard and accept a nested child in standalone F + I. This
  contradicts UIM-DT-01 10b.

**Recommendation: A.** It keeps core passive and reported; the only hosted change is a fixed
placement order (core after `fishball-instance` and the three features). Core's report cannot
tell an order miss from an owner override without reading the profile files, so both show as
`guards-overridden` naming the row. Rows of bundles core does not list (for example `agent-team`)
stay outside the guards either way; that is a separate scope decision.

### Q-S6-2. How does core remove the session-creating preset tools?

**Decided 2026-11-12: B, amended**: every shipped preset switched off (not deleted), core's
`fishball` and fishball-watchdog's `watchdog` presets, no migration, earlier sessions discarded.
Proven in §7.2–§7.3.

**Background.** The preset tools are rows inside each agent preset's `config.plugins`, and no patch
can address them. A static patch can only switch a whole preset off, or replace its whole config.
The fixture switches the shipped presets off and adds `fishball`. That works for new sessions. But a
V2 child's existing manager session, recorded under `standard`, then fails through the session
controller (`gateway/internal`), and on rc.5 its model is not even reached through `agents.resume`.
Redefining `preset-standard` in place keeps it resumable.

**Options.**
- **A.** Core **redefines the shipped `standard` preset in place** (same id, whole config replaced
  with Fishball's list), and disables the other three shipped presets. Migrated and new sessions both
  run `standard` = Fishball's composition; resume works through the controller on both SDKs.
  Downside: the owner's own edits to `standard` (Web preset editor) override core's, which is what
  Q20 accepts; and a future DSH that changes `standard`'s contents is masked.
- **B.** Core adds its own `fishball` preset and disables the shipped ones (the fixture). The
  migration then has to move the V2 session to `fishball`. `agentPresets.select(agent, id)` exists
  on both SDKs for a live agent, and `agents.resume` gives one, but S6 did **not** test it, and on
  rc.5 the resumed agent did not reach the model. Not proven.
- **C.** Core keeps the shipped presets and blocks the tools another way (an X19-like gate on tool
  calls). This contradicts "guards come only from core's patch" (R-FB-02, Q20).

**Recommendation: A**, plus a rule in core: at app ready, and whenever core's manager session is
resumed, it re-pins that session's sandbox and approval to the read-only preset (as V2's
`configure` does at create). Then a migrated session is read-only too. The override report compares
`agentPresets.defaultId` against `standard`, and reports any change to `preset-standard`'s
composition as `guards-overridden`.

### Q-S6-3. Is `approval.config.policy` an acceptable read for the approval default?

**Decided 2026-11-12: A** (Fishball), with one test per SDK.

**Background.** `ApprovalService` exposes its config (`config: Config`, public in the `.d.ts` of both
SDKs), but no getter for the default policy; `effectivePolicy` is private. Reading
`ctx.approval.config.policy` works on both SDKs today.

**Options.** **A.** Use it, behind core's existing version adapters (§9.2), with a test on each SDK.
**B.** Derive it from `permissionPresets.defaultPreset` + `resolve(name).approval`. That reflects the
*preset* default, not the row's own config, which is what an owner override changes.

**Recommendation: A**, with B's value reported too: the two together tell whether the owner changed
the row or the preset.

### 7.1 Core reorders the bundle list — PASS, one restart

| Check | rc.5 | rc.1 | Evidence |
| --- | --- | --- | --- |
| Order after native install | `[base, web-app, core, board, instance, watchdog]` | same | `decided-1-<v>` |
| When the reorder can run | in core's own `apply`, the first moment core's code runs; it succeeded (`moved: true`). It cannot run earlier: the boot that runs it was already composed in the old order, so `fishball-instance` is `on:active` at app ready in boot 2 | same | `decided-2-<v>` `reorder`, `rowsAtAppReady` |
| Manifest after it | `[base, web-app, board, instance, watchdog, core]` | same | `bundlesAfter` |
| Same boot, HMR on (standalone) | DSH's HMR watches the profile manifest and **recomposed live**; 3 s later the instance row is `off` and core's report is empty. The stand-in instance had already started once, then was stopped | same | `decided-2-<v>` `rowsAfterSettle` |
| Same boot, HMR off (hosted) | no live recomposition: the instance stays `on:active`, and core reports `[fishball-instance]` until the restart | same | `decided-nohmr-2-<v>` |
| Next start | the instance row is `off` from the start (never started); core finds itself last and writes nothing (`unchanged: true`); the app-ready report is empty | same | `decided[-nohmr]-3-<v>` |
| Conflict or preflight line | none, in any boot | none | `conflictLines: []` |

**It needs one restart** before the guards hold from the start. In standalone mode with HMR on, DSH
does the recomposition live, a few seconds after start, but the instance's row had already started
once. In hosted mode HMR is off (§6.2), so the restart is the instance's own child restart. The
child's first start after placement therefore runs one start with the instance row on, unless
**the instance places core last itself** (§8.1). That avoids it, and it is what
`hosted-core-last-<v>` already proved. Core's reorder is then only the standalone safety net.

### 7.3 A leftover old session is discarded, with no crash — PASS

The boot-1 session records preset `standard`, which is now switched off.
- `resolveAgent` refuses it with `gateway/internal` (the same as round 1; no throw escapes).
- `workspaceController.archiveSession({ sessionId })` succeeds and returns the archive set holding it.

- After a restart (boot 4) the leftover is still in the archive set (the workspace `follow`

### 7.4 Effect on the design and the cases
