## Results and delivery

`result_snapshot` is one scoped ledger snapshot with version/epoch, observation time and evidence reference. It exposes existing Foundation task statuses; `dispatchPaused` is a separate candidate dispatch fact, not a new W1 task status. Reports reference original goal, actual completed scope, unfinished work, next step, blockers and verification evidence. `not_run` is explicit; `passed`/`failed` needs nonempty evidence. Artifact records bind artifactRef, immutable version/content digest, contentRef and production evidence. Artifact review binds the task version, artifact version/digest and independent reviewer session generation. Production or worker self-report does not establish independent verification.

Before reporting reviewed success, trusted code compares current scope/taskVersion and artifact bytes/version with every review binding; changed bytes invalidate an old review as `stale` even if the display name is unchanged. Review/provenance refs are references to checked durable facts, never grants. Permission/current recipient checks apply independently of review.

Each delivery item binds actionDigest, taskVersion, artifact version/digest, batch/item/delivery/attempt/command identities, recipient and channel references, and separate historical delivery and current permission/openability facts (dated by accessObservedAt). Its normalized immutable action spec includes scope, task/artifact versions, bytes, exact recipient and channel. The durable idempotency key is scoped delivery intent + batch/item + exact version/digest/recipient/channel; command reuse with changed immutable content is rejected rather than assigned a new key. New attempts reconcile the same intent before admitting a distinct attempt and preserve its audit lineage. Sent/delivered/unknown records retain claimRef and reservationRef; neither unknown nor notification failure automatically releases accountable budget ownership.

`pending`, `accepted`, `sent`, `delivered`, `failed` and `unknown` remain separate from task completion and verification. Delivered requires receiptAccess recording granted permission and verified opening at receipt time, plus recipient evidence for the exact bytes/version/channel. The separate permissionState/openability/accessObservedAt fields report current access: a later permission revocation can yield delivered plus current revoked/failed access without erasing the committed historical receipt. Structural presence alone proves neither receipt nor access. Raw local paths, expired or wrong-version links cannot establish a new delivered receipt or current verified access. Unknown send results require channel query first. A confirmed failure permits retry of that item only after trusted negative effect evidence and current authority/admission checks; a failure code alone is insufficient. A partially delivered batch preserves successful items and never resends the whole batch. Quiet hours, important blocker exceptions and progress coalescing are policy decisions: `progressDigest` deduplicates unchanged factual scope/status/blocker/decision/evidence, while notificationDisposition records changed/coalesced/suppressed/blocked-policy facts without selecting a policy.

## Optimistic controls and snapshots

`control_command` contains shared binding (scope, expectedTaskVersion, expectedAuthEpoch, commandRef), normalized actionDigest and displayed/permission snapshot references. `operatorContextRef` is an audit reference, not a serialized operator capability. The actual trusted host/operator capability authorizes a control and current ledger state determines applicability. Double-clicks with the same immutable command return one persisted outcome; a changed spec under commandRef conflicts. An old tab/epoch cannot overwrite current state. Pause blocks new dispatch and cannot claim all in-flight actions stopped. Resume cannot bypass recovery, unresolved approval or reservations. Cancel follows Foundation's serialized cancel/claim order and reports actual stage rather than click acceptance.

`control_outcome` distinguishes applied, rejected, stale, unknown and partial, with authoritative observed taskVersion/authEpoch, snapshot/evidence refs, dispatch, termination and preexisting effect axes. Stale requires a fresh authoritative read; unknown/partial requires effect reconciliation. A cancel with in-flight work may be partial: dispatch blocked, termination requested, effects unknown. A completed effect is retained. Applied pause/cancel and partial pause/cancel require dispatchState blocked; this bounded structural condition does not establish termination. Applied means the specified ledger control took effect, never that an arbitrary external effect was undone or all workers terminated. The schema intentionally does not prescribe the future pause/resume transition table; implementation must freeze it against every current Foundation status and applicable capability before admission.

List/detail use the same transactional snapshot or explicitly show differing snapshot versions and observedAt. Refresh queries authoritative state before rendering a new snapshot. permissions.allowedCommands is a factual display hint; controls are checked again under the mutation lock. Terminal snapshots offer no mutation commands. Session, artifact and grant links are checked against trusted owner/workspace/task and live session generations; refs do not authorize shortcuts. Unknown contract versions/fields, missing native capability and stale permission fail closed. UI transport disconnect/reload cannot manufacture an applied outcome.

Sixteen artifacts, deliveries per artifact, related sessions, grant refs, blockers or report evidence entries are candidate wire ceilings only. No artifact type, report depth, retention/lifetime, cost threshold, provider, license or real DSH extension entry is selected.
