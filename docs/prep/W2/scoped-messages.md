## Envelope and trust

An envelope records scope, taskVersion/authEpoch, optimistic binding, immutable message identity, sender and receiver **sessionRef plus generationRef**, bounded referenced payload, message category and purpose. `sourceIdentity.sourceRef` identifies the qualified source namespace (including any provider/source identity) by digest; `eventRef` identifies that namespace's event. `dedupMode: unavailable` requires `dedupWarning: no_unique_source_id`; eventRef then denotes a local surrogate and cannot imply source uniqueness or safe replay.

Trusted adapter activation freezes caller owner/workspace/task and session generation, checks live target ownership and lifecycle, and compares every envelope identity against that immutable context and current ledger. Payload refs, `grantBinding`, evidence labels, parent/child relationships and model summaries supply no authority. A reused sessionRef with a new generationRef never inherits mappings/grants. Runtime checks unavailable native capabilities before accepting work and rejects unknown contract versions/fields or unsupported capabilities fail-closed. No DSH model/catalog, provider or first cross-task scope is selected.

`grantBinding` describes an exact candidate ledger binding: scope, taskVersion, task authorization epoch, grant version/expiry, sender/receiver generations, category, normalized actionDigest, target/data/limits digests. At one transactional dispatch claim, compare these values with the trusted current grant, expected taskVersion/authEpoch, purpose, payload digest, active reservations and expiry read after the lock. Complete normalized immutable content includes the original origin/purpose, endpoints, category, scoped message/source identities and target/data/limits; changing any of it under the same message/command identity is a dedup conflict. Neither matching refs nor schema-valid grants authorize dispatch. Mapping this candidate to Foundation's existing exact action/grant binding needs separate implementation review.

## Ordering, outbox and forwarding

Preserve Foundation intake uniqueness as owner + workspace + provider + source + event; taskRef is its established association, never a way to rebind the same source event to another task. Persist a unique outbox record using owner + workspace + task + qualified source/event identity + messageRef + sender generation + receiver generation. Bind its immutable content digest, commandRef, claimRef and reservationRef in the same atomic authority/admission claim; known duplicate content returns the existing record, and conflicting content is refused. Do not incorporate new content into the key to permit changed-message replay. Without unique external IDs, record degraded dedup capability explicitly and require reconciliation/manual resolution of ambiguous duplicates.

Revoke-first rejects as `grant_revoked` and creates no dispatch claim; rejected records structurally forbid outboxRef, claimRef, reservationRef and receipt linkage. Claim-first commits accountable outbox intent before transport and remains in flight if revoke/cancel follows; new claims are blocked. `accepted`, `outbox_committed`, `sent`, `consumption_confirmed`, `unknown`, and `rejected` are separate proposed message facts, not task statuses. Accepted records have not claimed dispatch; committed/sent/confirmed/unknown records retain outbox, claim and reservation linkage. Consumption requires independently verified receipt provenance bound to the scoped message, receiver generation and immutable bytes. A timeout becomes unknown and `query_required`; it cannot prove nondelivery, release capacity or authorize blind resend. Reconcile receipts/channel records before any bounded new attempt. Arbitrary recipient effects do not have an exactly-once guarantee.

A forward preserves the immutable `originalSender` and `originalPurposeRef` and appends the forwarding session's generation to a bounded route. The schema ceiling is eight hops/nine visited generations and 65,536 referenced payload bytes; these are preparatory wire ceilings, not selected operational defaults. Runtime verifies hopCount <= hopLimit, path/count consistency, origin/purpose equality with the prior immutable record, and no repeated generation. Each forward needs a current exact grant for its own sender/receiver; a parent relationship grants no unrelated route access. Reject cycles and limit excess before adding an outbox claim. Out-of-order messages may be retained as historical facts but cannot overwrite newer task state.
