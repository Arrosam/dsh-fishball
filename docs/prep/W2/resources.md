## Candidate wire axes

| Envelope | Proposed meaning | What schema validation cannot establish |
| --- | --- | --- |
| `admission_request` | Current task/auth CAS, resource/model policy versions and complete normalized immutable action spec presented to a future atomic claim. | Trusted caller identity, current versions, digest equality, model availability, expiry ordering, remaining budget or permission. |
| `reservation_snapshot` | Exact claim ownership, weighted role units and held/released lifecycle facts. Unknown and cancel-requested observations remain held. | An actual executor's existence/termination, receipt trust, current session generation or atomic release. |
| `budget_policy` | A versioned resource policy proposal. Lower limits preserve existing reservations and may pause or drain new dispatch. | Owner authority to change policy, arithmetic comparing observed usage with a limit, or successful enforcement. |
| `usage_observation` | Usage quantity labeled actual, estimated or unknown; cost certainty is separate. | That a provider reported the quantity, the validity of an estimate/error bound, attribution or a final bill. |
| `control_request` | Bounded status/stop/revoke/pause commands which require no extra model worker. | That the caller may issue the command, control latency or successful termination. |

All envelopes and nested objects are closed. References use the shared lowercase SHA256 primitive; references are equality keys, not credentials. Common `binding` maps to future trusted scope plus `expectedTaskVersion`, `expectedAuthEpoch` and a scoped idempotency `commandRef`. Expected versions are preconditions, not instructions to replace ledger state. JSON cannot establish equality between repeated fields or authenticate an evidence label.

## Atomic claim and immutable policy

The candidate runtime claim must share one transaction domain with the authoritative task, action, authorization, attempt counters, active weighted reservations and resource policy. Separate caches or provider/model summaries cannot decide capacity. The trusted adapter derives the domain and scope; a payload cannot choose a different resource pool to escape a limit.

Role classification, weighted units, attempt groups and reserved runtime/usage charges must be derived or checked against trusted current policy. A payload cannot declare itself a cheap reviewer/control command or report zero estimated charges to bypass accounting. Unknown actual usage remains an explicit obligation; dispatch estimates are not measurements. Before any native creation or effect, under the mutation lock:

1. Validate current task version and authorization epoch, exact consent, permission and strict expiry after lock acquisition.
2. Match the complete normalized action specification and canonical `actionDigest`, including target/data, weighted units, attempt group/index, role, task/auth/resource/model bindings, immutable model policy, accounting charges and pre-dispatch generation/environment/tool/permission bindings. The top routing binding and policy mirrors must equal the immutable spec; JSON cannot prove that equality. Same `commandRef` with different content is a conflict, not durable deduplication success.
3. Validate current resource-policy and model-policy versions. Reject stale policy snapshots and silent substitution; an unavailable or unverified model blocks this dispatch. A host capability probe and later trusted catalog adapter are prerequisites, not fields that confer availability.
4. Check queue, active units, attempts, runtime/usage dispatch budgets, metadata/storage bounds and protected reconciliation history together. Reviewer and repair work use the same domain and account for their units/time/usage/attempts. No reviewer or repair role grants a free worker.
5. Commit the exact claim and reservation before calling any native provider. No await or provider callback occurs inside this transaction. Failed admission commits no intent, no slot and no attempt charge.

Resource and model policy versions are separate immutable candidate ledgers. They are not new schema2 columns or W1 methods. An implementation must freeze each admitted claim's versions/spec and record subsequent policy revisions separately; rewriting an in-flight claim to use a newer policy is forbidden. A scoped command retry can return its original durable claim; an actual additional native attempt needs a distinct admitted claim and cumulative accounting. Idempotent retries do not conceal another native call or consume a different immutable spec under the same claim.

Usage limits here describe dispatch budgets. Missing actual usage keeps uncertainty visible; it cannot be replaced by invented zeros. Reserved estimates and actual usage require an explicit trusted reconciliation policy before availability is recomputed. A slow report cannot retroactively authorize dispatch that was denied. W1’s existing per-task/per-kind maximum-attempt count remains distinct from these proposed total session/runtime/usage budgets; no current W1 API adds total budget enforcement. Aggregate future attempts and charges include worker, reviewer and repair runs; failing or uncertain runs remain accountable. Both `perGroupAttemptLimit` and `totalAttemptLimit` must apply: inventing another group cannot reset the total allowance. An exhausted automatic attempt group enters a reported blocked condition, with no automatic extra review/repair worker outside the same limits.

## Ownership, uncertainty and release

The candidate claim owns `reservationRef` and `claimRef`; the full immutable spec and worker mapping bind the same `actionRef` and canonical `actionDigest`, immutable `generationRef` and any already-known `sessionRef`. `executorBinding.mode: create` has no session reference in the approved intent; `resume` requires an already-known session reference. A newly observed created session attaches through a receipt/map bound to the original action digest, claim and generation, without modifying or re-hashing the approved spec. Canonical serialization/digest implementation is deferred; later cross-lane equality tests must verify this exact meaning. A generation is assigned before creation; an unknown creation may have no session reference. Reused native session IDs cannot inherit a reservation, approval or outcome from another generation. Action/spec, scope, task/auth versions, session/generation and claim references must match trusted observations before reconciliation. Cross-envelope equality is a runtime invariant, not JSON proof.

The bounded `uncertaintyAxes` explicitly covers worker creation/execution, action effects, message consumption, delivery and handoff. Unknown snapshots require at least one unresolved axis; released snapshots carry none. Unknown worker creation, unconfirmed execution timeout, action effect, message consumption, delivery or handoff retain accountable reservations. A cancellation request or revoked approval prevents future claims at the ledger's ordering point but does not prove an existing executor stopped. Dispatch-first remains in flight/unknown; revoke/cancel-first prevents dispatch. No blind create/recreate/resume/replay/resend, autonomous orphan deletion, instant cancellation or completed-effect rollback is proposed.

A resource release requires three distinct facts: `terminalEvidence` proves exact executor absence/termination, `outcomeEvidence` reconciles all outstanding outcome obligations, and `releaseEvidence` records the trusted ledger’s atomic release after checking the first two. All bind the exact claim/generation. Held snapshots may carry partial terminal/outcome facts but forbid release evidence or a release basis; neither partial fact frees units. `releaseBasis` is `confirmed_no_executor` or `confirmed_stopped_and_settled`, matching the worker lane’s confirmed release conditions; the latter requires an observed session reference. These labels and empty uncertainty arrays remain claims to verify, not self-authorizing release facts. A known action effect alone cannot free units while its executor may still run. Creation proven not to have occurred can release without an invented session ID. An observed stopped executor with uncertain message/delivery/effect obligations remains held until those obligations are reconciled. Repeated unknown or already-invalid revocation observations are idempotent and must not exhaust protected reconciliation history. Released reservations keep immutable evidence and historical accounting; late/stale results cannot release a newer generation or erase cancellation/regrant facts.

This proposal must be mapped deliberately to the [worker lifecycle lane](worker-lifecycle.md) and message/delivery lane. It does not expand the W1 `settle` API into a worker termination oracle.

## Downshift and responsiveness

A resource-policy downshift is a versioned owner operation in the same transaction domain. Existing held units can exceed a newly lowered active limit. The response is to preserve obligations and reject new work until available capacity/budget permits it, or to pause/drain admission. Lowering a cap cannot release slots, reset attempts or rewrite usage. Requested cancellation of existing work follows the ordinary evidence-based lifecycle. Fresh work after a downshift must use the current resource-policy version; claims serialized earlier retain their original accountable spec and charges.

The main conversation must retain a bounded control/intake path whose handling does not wait for long-running work or require another inference session. The candidate control envelope allows status, pause, revoke and cancel; `revoke_action` requires exact `actionRef` and immutable `actionDigest` in addition to scoped task/auth CAS, while task-wide controls exclude these action-target fields. `commandRef` only deduplicates the command; it never selects a latest action. It cannot request an uncounted worker. Trusted code classifies commands, applies a separate finite control queue/rate bound and serializes brief mutations with the authoritative ledger. Payload priority flags cannot mint control privileges. If a control action itself needs a worker, it must become an ordinary accounted admission claim. UI responsiveness and cancellation/effect timing are separate observations.

There is no chosen control latency, main-input response objective, worker count, weight schedule, time ceiling, monetary threshold or throughput promise here. D3/D10 and actual native load tests must select and measure those values. Saturated work intake must return stable bounded overflow results while trusted stop/status controls remain responsive within the later agreed objective. Control overflow itself must also be bounded and observable.

## Usage and cost provenance

Actual usage is a quantity with trusted source evidence, attribution to an exact claim and defined units. Estimated usage includes a source/method reference and a finite error bound or explicit unknown uncertainty. Unknown usage has a reason and no quantity; zero actual usage is distinct from no report. Cost has its own actual/estimated/unknown label and provenance. Currency strings and synthetic fixture amounts do not verify prices or billing. A provider usage receipt and a bill are different facts.

Admission `charges.costEstimate` is estimated or unknown; it cannot claim actual monetary consumption before an effect. The candidate cost policy either names unresolved D10 (`decision_pending`) or supplies a versioned estimated dispatch-budget currency/limit/source with `block_budget_dependent_dispatch` when valuation is unknown. The mock vectors use D10 pending and unpriced model estimates, without selecting a monetary threshold. Future trusted policy must reject cost-budget-dependent dispatch until the relevant owner decision and source checks succeed; a shape-valid mock request does not imply it is admitted. Estimated monetary reservations and later actual cost observations must aggregate across worker/reviewer/repair claims without resetting or rewriting historical charges.

The candidate policy fixes `enforcement: dispatch_budget_only` and `hardBillCap: false`. These are contract constraints, not proof that a host enforces a ceiling. No exact price, hard billing cap, immediate force termination or absent-host capability is claimed. A stale estimate, partial receipt or unavailable accounting source must remain explicit rather than fabricated.

## Verification limits and pending integration

The 20 vectors test structural boundaries and state-specific wire assertions only. Finite JSON bounds do not select safe product thresholds. Schemas cannot calculate digest equality, version freshness, arithmetic capacity, expiry relative to trusted now, cross-field/generation identity, evidence authenticity, atomic reservations, actual usage, cancellation or latency. A schema-valid released snapshot is still untrusted data until the ledger verifies its evidence; it is a proposed observation shape, not an independent command to free units.

Root owns the common schema and local verifier. This lane does not install a validator, load native services, mutate Foundation, run inference, inspect credentials, navigate browsers or perform Git operations. W1 browser HOLD, later resource/model catalog bridge, production retention and actual usage/performance acceptance remain open. Final preparation review must resolve cross-lane names and verify the exact frozen artifacts; preparation success does not waive the W2 production dependency gate.
