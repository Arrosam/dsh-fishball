## Candidate operations and ordering

The six operation names are proposed bubbles envelopes, not native DSH methods. Every envelope carries factual `scope`, `taskVersion`, `authEpoch` and immutable evidence. Mutation payloads carry the shared `binding`. An envelope validates structure only; its facts and apparent roles do not authenticate its caller or grant permission.

| Operation | Proposed meaning | Future admission/ordering requirement |
| --- | --- | --- |
| `register_intake` | Register immutable provider/source/event identity and payload reference before classifying pending/new task/supplement/control. | Derive scope from trusted ingress. Uniqueness key is owner/workspace plus complete provider/source/event identity, consistent with Foundation ingress; taskRef is the associated task, not an additional deduplication key. Identity collision with changed digest is a conflict, never a replacement. Repeated delivery returns the existing entrance; a changed proposed taskRef must not create another entrance or rebind the existing task association for that identity. Intentional new ID survives identical prose. Task association and remote-entry pairing need the trusted adapter policy; no provider selected. |
| `revise_task` | Propose replacement reference/digest and the bounded fields it changes. | Compare binding scope/version/epoch and normalized content under the future ledger mutation lock. A successful actual mutation increments current task version; conflict does not overwrite. Newly assembled work uses that version; older completions cannot overwrite it. Priority is a field proposal, not a selected scheduling policy. |
| `request_stop` | Record the user's requested cancellation. | Atomically block new dispatch first, then request cancellation through a capability-probed future native adapter. Claim first keeps prior work accountable; stop first prevents the new claim. Actual APIs and termination evidence are still unverified. |
| `clarify` | Keep one reference-based decision batch and its dependent branches in awaiting/answered/withdrawn state. | Gather only necessary unresolved decisions. Continue independent work; pause only dependencies. An answer needs immutable content digest and a trusted attributable response. Known context resolves decisions without repeat questions. Silence cannot produce answered state or consent. |
| `assemble_context` | Reference a scoped, versioned briefing and its provenance, current ledger read, facts, conflicts and limit decision. | Re-read completion and authority from the ledger at admission/recovery and again at dispatch claim. Resolve current instructions over older summaries, and ledger authority over summary claims. Query stale host facts when the dependent action needs them. |
| `coordinator_outcome` | Return a bounded stable code and separate cancellation fact where applicable. | Accepted registration is not a dispatched action, completed task, delivered message or confirmed cancellation. `recovery_required/unknown_outcome` preserves uncertainty and reservations until reconciliation. |

`recordedOrder` is a proposed committed ledger order within the task, not the provider timestamp or global causal clock. Concurrent remote inputs and corrections/completions need serialized ledger mutation plus CAS. Version values cannot wrap: the maximum safe integer is a structural ceiling; implementation must fail closed if no successor is representable. Deleted source messages cannot erase durable ingress identity or authorize replay. Pending intake classification does not block accepting another bounded message or querying status; scheduling/backpressure must preserve those control paths under BUB012 limits. No latency target is selected here (D3/D10).

Schema names require an explicit later bridge: Foundation currently accepts trusted raw identifiers and persists hashed refs, and uses `expectedVersion` rather than this proposal's `expectedTaskVersion`. Do not pass hashed candidate refs into Foundation raw-ID arguments for rehashing; the future trusted adapter must preserve identity and explicitly resolve/map references. Revisions may change goal/constraints/pending decisions/priority; completed-step facts are ledger-derived and cannot be established by a user-material update. If a later briefing binds a dispatch action, the shared `actionDigest` must cover the complete immutable normalizedSpec (target, data digest, operation and bounded units), not merely briefing or output content. This candidate briefingDigest binds only briefing content and grants no dispatch permission. Schema2 task statuses and tables are unchanged. Nested/envelope scope equality, current versions/epochs, duplicate content equality, idempotency and atomic ordering require runtime checks; JSON Schema deliberately makes none of those equality or trust claims.

## Context and data boundary

Each material has reference/digest, source scope/task version, `materialKind` classification, observation time and snapshot freshness. Summaries additionally require generation time and bounded source refs. Goal, constraints, pending decisions and completed steps each have an immutable reference, including an empty-set artifact where relevant. Recovery rebuilds these latest facts from their sources rather than replaying an old summary. Conflict records preserve winning/superseded refs and a stable reason; neither a summary nor a current-instruction record can grant authority. Wall-clock age is informational until D8's trusted clock, freshness and retention policies are selected.

Context readiness declares relation to an externally selected context policy: below/at may be ready; above requires compression or rejection. Compression references independent coverage evidence and an after relation of below/at. These declarations do not measure tokens or prove constraint preservation. Future assembly must retain goal, critical constraints and refusal/authority boundaries, or reject; missing/deleted source and unavailable retrieval cannot silently drop required facts. The candidate finite list caps (16 materials/source refs/decisions/branches, 8 conflicts, 4 changed fields) bound wire structure only and do not choose model limits or D8 defaults. Selected model/tokenizer, measured N-1/N/N+1 counts and accounting belong to the later implementation.

Briefings give a worker only material required by its task. Matching payload scopes are insufficient: trusted source access and final assembly must reject other owners/workspaces/tasks and inspect the actual native model input. Host facts are always snapshots here; `requery_required` demands a fresh capability-supported query before dependent work. The ledger reread's version/epoch must match current trusted state; a wire evidence source label is not provenance proof.

All payloads are reference-only. No prose, questions, answers, summaries, credentials, exceptions, personal memory, executable paths or artifact contents enter these metadata envelopes. A separate bounded scoped data plane must supply verified digest resolution, access control, retention, deletion and secret handling before execution. D4/D5/D6/D8 remain unresolved. W3 memory/BUB007 integration is excluded. Ref-only fixture validation cannot verify digest contents, data-plane retention or actual prompt isolation.

## Errors and uncertain outcomes

Stable error codes cover stale version, scope mismatch, missing source, context limit, unavailable capability, storage fault and unknown outcome. Unknown/future fields and contract versions fail closed. Reject before side effects when state/storage/capabilities cannot be checked. A timeout does not establish no session/effect, and a stop request cannot report observed termination. Unknown outcomes keep accountable reservations and need independently trusted query/receipt evidence before retry. Late results remain evidence but cannot regress current or terminal task state. No automatic replay, instantaneous cancellation, effect rollback or exactly-once external effect is promised. Message/delivery/worker evidence remains owned by the other lane contracts.
