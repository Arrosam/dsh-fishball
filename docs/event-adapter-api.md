# Native event, schedule and provider-neutral chat contracts

These are optional trusted-installation capabilities on pinned DSH Web0.2.1-alpha.1. Verifier/permission/normalizer closures and opaque registration tokens are never accepted from RPC JSON or exposed through `ctx.df`. Source/subscription configuration and exact missed-plan approval use the native authenticated owner; only Ledger admits durable tasks. No adapter launches a worker, grants an action, sends an effect, installs an account or runs a daemon by receiving an event.

## EventRouter

`register({sourceRef,subscriptionRef,adapterRef,providerRef,sourceIdentityRef,verify,authorize,isCurrent,normalize})` returns a process-private opaque token. All refs are SHA256 references to explicit installation facts. `verify` receives a captured bounded payload and returns `{providerRef,sourceIdentityRef,eventIdRef?,observedAt,routeBinding?,eventKind?,requestDigest?}`. The implementation of provider authentication is the installer's responsibility; a payload signature/owner/verified flag is not proof. `authorize` must return strictly true; synchronous `isCurrent` runs again immediately before the core transaction. The native core rechecks enabled source/subscription revisions, task CAS, route, age, rate, queue and clock inside that transaction.

`ingest(token,{commandRef,taskId,payload,clockRef?,expectedCursor?,scheduledAt?,verificationPlanDigest?})` commits one encrypted new-task goal or protected supplemental instruction and a scoped durable event receipt. The provider/source/original principal/conversation/thread/event ID determines identity; changing subscription, source revision or pairing revision cannot mint a fresh copy of the same event. Same ID with changed material conflicts; distinct IDs retain intentionally repeated text. Missing provider IDs explicitly degrade to same-command deduplication, with no safe arbitrary resend guarantee. The returned registration fact is separate from processing/completion/unknown readback.

Payloads are captured before awaited callbacks, limited to65536 serialized UTF-8 bytes **inclusive**, with strict JSON descriptors/Unicode and registered-secret rejection. Closed request metadata is captured/bounded separately; trusted source/subscription/proof envelope overhead does not reduce this payload quota. The returned authentication envelope joins already recursively frozen components; it cannot enlarge the incoming payload allowance. There are128 registrations and32 pending authentication/ingress operations. Source/event lifetime capacities and retention refusal are in [the authoritative API](runtime-automation-api.md); no dedup knowledge is evicted to make room. `unregister` and `dispose` invalidate late callbacks. There is no automatic callback retry.

## ScheduleDriver

`register({sourceRef,subscriptionRef,adapterRef,providerRef,sourceIdentityRef,spec,startAfter,goal,externalEffect,authorize,isCurrent})` returns a private token. The source must be kind=schedule/identityMode=unique_id, and subscription.triggerRef must equal the canonical complete scheduleSpec digest. `spec` is the closed interval/daily/IANA/DST/missing-time/catch-up/age/scan policy in event-clock; every behavior-affecting choice is explicit. `startAfter` is an exclusive initial UTC cursor, not a fabricated persisted clock.

`tick(token)` returns not_started/nothing_due/skipped/verification_required/admitted. Coalescing selects the newest eligible due occurrence and admits one task. Skip advances a durable cursor without a task. Verification persists the exact plan while retaining the prior cursor; only `approveEventClock` with the private owner and exact plan/revisions can unlock it. Approval still admits only task ingress: every later effect needs its separate full action/data/consent/budget claim. A failed queue/rate/CAS/age admission retains the pending plan and cursor. Source/subscription revision changes cannot inherit old approval. Unknown actions are never replayed from a missed timestamp.

`status(token)` exposes UTC cursor, timezone, revisions and pending plan metadata. `start(token,{pollMs,onStatus})` explicitly enables an owned host timer; pollMs is60000..86400000. No timer starts during registration. `stop` invalidates the current private polling lifetime, including fired/queued timer callbacks awaiting authorization; restarting creates a distinct lifetime so old callbacks cannot admit, clear the new timer, publish or reschedule. An explicit manual `tick` remains independent of polling and may run after stop. `unregister`, `dispose` and plugin quit invalidate the registration and all pending work. Previously committed tasks/cursors remain durable facts; stopping cannot undo them. Observer failure does not change the committed admission or generate a second notification. A backwards persisted clock or over128-occurrence/scan gap fails for review without clearing the cursor. Ordinary no-due ticks may advance a checked empty cursor. The clock is a scheduling proposal, not provider availability or external replay evidence.

## ChatAdapter

The owner selected **no live chat platform this phase**. This module validates DF010-C01..C05 only. Its synthetic tests are neither production connectivity nor provider-specific delivery acceptance. Actual chat software/accounts/platform auth are out of phase.

Construction requires the same explicit source/subscription refs and private callbacks plus `maxAttachments`0..16 and `maxAttachmentBytes`1..8388608. The source is chat with a privately admitted private conversation/pairing/principal/thread route. `verify` supplies eventKind=message/edit/delete/status/control/attachment. Authenticated edits/deletes require a fresh explicit instruction and cannot silently modify a task. `normalize` returns `{content,attachments}`; the encrypted `df.chat-input/v1` retains original route/event/material. No control proof is inferred from content or forwarded identities.

`status({taskRef,payload})`, `control({taskRef,expectedTaskVersion,expectedAuthEpoch,kind,payload})`, and `readAttachment({taskRef,attachmentRef,payload})` require the private proof's requestDigest to equal the canonical exact request. Status intent is `{kind:'status',taskRef}`; control intent is `{kind:'control',taskRef,expectedTaskVersion,expectedAuthEpoch,control:kind}`; attachment intent is `{kind:'attachment',taskRef,attachmentRef}`. Pause/resume/cancel are the only remote controls. A complete original provider event identity derives control commandRef; caller command IDs cannot cause duplicate control. Group/new pairing/wrong window/thread and stale/revoked bindings fail. There is no remote grant endpoint.

Closed attachment descriptors are `{attachmentRef,sourceRef,routeDigest,digest,byteLength,name,mediaType,permissionState,observedAt,expiresAt,evidenceRef}`. They must carry granted private access evidence and exact admitted source/route, fit explicit quotas and remain unexpired. The read path accepts only record/digest bindings in the authenticated original event receipt, excluding owner-created lookalike context. Older events lacking a goal binding remain unchanged and provide no attachment proof. A trusted optional reader must return exact bounded bytes/digest/access evidence; permission and expiry are rechecked after await. Returned bytes are a copy. Conflicting descriptors require a new identity/version. Local paths and payload access flags are not delivery or source evidence.

Optional `outbound={authorize,isCurrent,send,query,open}` supplies a private recipient adapter to the existing [ResultPipeline](runtime-api.md). It derives recipient and channel from the original admitted route, checks current Ledger association after awaited permission, and invokes the provider callback only after exact outbox/resource admission. Callback throws become unknown; no blind resend follows. Sent, verified delivered, and subsequent current accessibility are distinct. Reconciliation and known-failed retry retain the original immutable version/channel/data and held resources. A later access failure preserves historical delivered state. Live delivery remains out of phase.

All instances dispose with the host. Current module tests use actual encrypted RuntimeStore and synthetic private provider callbacks; actual Web UI, catalog/model/tool production behavior and final independent code review remain separate acceptance gates.
