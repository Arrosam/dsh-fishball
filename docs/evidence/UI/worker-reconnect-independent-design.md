## Original public lifecycle and independent requirements

The ConnectionHandle has state and generation stores, each with getSnapshot and subscribe. State is undefined before the first connection outcome, then connecting/connected/disconnected; generation is undefined before readiness and during recovery/loss, otherwise a stable object with a monotone id within that Client runtime and host facts. Stable snapshot identity across unchanged reads matters; creating a new snapshot object on each render is not the original store contract. Host facts and ctx.remote.$host.home can remain cached; they do not establish current event delivery.

Original ConnectionController waits for a source whose incremental listeners are attached before ready(host), emits state connected, then invokes onConnected. Original installConnection publishes the generation during onConnected; original Gateway emits connection/reset afterwards. Thus the real initial order is source ready -> state connected with no new generation yet -> new generation snapshot -> Gateway reset. Loss clears generation before publishing a nonconnected state. Start is owned by Gateway; a second ConnectionHandle.start is refused, while controller start is internally idempotent. Consumers subscribe to the existing service; they do not open a second loop to repair UI state.

The original source must stop delivery, release resources and settle after abort before a replacement starts. Connection reconnect replaces the attempt immediately, and browser offline suspends automatic retries. Gateway disposal stops its loop and waits for forwarded listener/stream work. A business listener exception is contained by the original Connection stores/controller. These are public dependency facts, not proposed DF implementation branches. A direct ConnectionController constructor is declared but its usable installed runtime export path is not verified here; fixtures should exercise it through the genuine exported installConnection service unless that path is independently proven. Likewise use original Gateway apply and owned disposal, not a presumed private Gateway controller getter.

The worker UI must:

* Treat recovery as both state connected and a genuine current generation under the active original connection owner. HTTP/setup/task/catalogue success or cached host facts alone never imply a live event stream.
* Reconcile initial/bootstrap and setup-ready transitions, mounting after readiness, Gateway reset and generation/state loss. Clear stale worker decisions, previews and grants before publishing a recovered view.
* Refresh only readonly status/catalogue/policy information on recovery. Never auto-confirm policy, plan/grant/create/execute, replay a task or produce a worker/result.
* Preserve needs_policy and the existing explicit policy-consent flow. A healthy connection is not policy acceptance. Future decisions require freshest original source, task/auth, permission/policy and expiry facts.
* Reject late readonly responses after loss, generation/owner replacement or disposal. A fresh response in a later generation is not overwritten by an older response.
* Show truthful unavailable/offline/request-failure information and permit bounded normal readonly rereading; no page reload, control bypass or unbounded refresh loop is required.
* Keep repeated reset/refresh behavior coalesced or finite and readonly, with clean subscription lifetime and no late publications/task duplication.

## Fixture/effect budget and finite observations

There are 36 unique cases: 27 UI_CONTROLLER_READONLY, 5 ORIGINAL_CONNECTION_PUBLIC and 4 ACTUAL_WEB_VISUAL_HOLD. All are NOT RUN. EP means equivalence partitions; BVA means selected boundary representatives; ST means state transitions; DT means decision table; RACE means async/lifecycle races; CO means conservation/effect counts.

Define one readonly recovery batch B as at most three actual existing requests supplying status/catalogue/policy-preview information; an endpoint may supply more than one logical read, so do not double-count a combined response. The exact existing endpoint names/signatures must be pinned by the fixture author. For an ordinary case, baseline plus at most one explicit refresh/recovery is at most two batches/six readonly requests. No mandatory request count or forced policy preview is implied. In every case, mutation count M = 0: no policy confirmation, task intake/control/revision/duplication, plan/grant/create/execute/capture/finish, model request, delivery or publication. A future separately authorized real policy confirmation is outside this readonly execution budget; its prerequisite consent presentation is covered here.

The burst representative is exactly eight reset/refresh notifications. Coalesced behavior may use at most two batches/six requests; a finite implementation may use no more than baseline plus eight batches/27 requests. In either case it issues no self-sustaining requests without a new input and no mutations. A finite source-recovery fixture opens at most four controlled original source attempts and stops via the public owner controls; it does not change the production controller's continuous recovery policy or claim retries are task replays.

Use real stable original snapshots or stable valid readonly DTO-store snapshots. Record public snapshots/listener publications, Gateway reset events, request endpoint/count, generation id/owner identity, safe phase/reason, busy/failure/consent UI state and task references. Never read a token or private controller field. A public deferred readonly RPC response is a legitimate race barrier; changing candidate internals or private methods is not. A deterministic unit source may attach its synthetic listeners, call the public ready callback, remain pending and settle on the actual AbortSignal; that is unit connection behavior only.

Suggested fixture bounds, to be sealed by root: <=2000 ms per ordinary unit case, <=5000 ms per four-attempt public connection case, <=120000 ms for the whole unit lane and <=120000 ms for each actual UI observation case. Controlled public connection timing may use warn W=50 ms and readiness deadline T=100 ms through the original ConnectionRecoveryConfig, with 20 ms fixed backoff. Observe W-1/W/W+1 and T-1/T/T+1. At exact T, classify whether ready or actual abort won; do not invent a millisecond-order oracle. A hung readonly request or unsupported public timer/disposal seam is HOLD if it cannot be bounded or safely superseded. No private/global clock patch, listener teardown or repeated real recovery attempt is authorized by this design. These are proposed finite harness limits, not facts that the model currently has a timeout API.
