## Required submission distinction

Before a request reaches the observable synthetic carrier, a proven local digest/build/validation/currentness failure is NOT_SUBMITTED. Its submitted count is zero. It may be retried only as a fresh explicit user decision with all current prerequisites after the failure is resolved. A failure message alone does not establish this boundary. A public invalid-input or declared dependency rejection is an acceptable unit stimulus; a private digest/helper override is not. Unsupported deterministic digest/build barriers remain HOLD.

After the synthetic RPC carrier accepts a mutation-shaped request, its simulated submitted count is one. Loss of reply, rejection/timeout without definite correlated nonapplication facts, reset, generation replacement, task change or disposal leaves SUBMITTED_UNKNOWN. Never automatically resend, rebuild with a new command, change a claim or treat current readonly success as proof the mutation did not occur. Invoking ClientConnectionRpc.call on a real carrier is not proof that bytes reached a host; the conservative real disposition is still unknown unless a genuine public pre-submission/nonapplication fact exists. These tests measure explicit synthetic acceptance, not real transport/native effect.

Retain correlation for the original operator/context, task, operation and request/command/action/data/claim/generation/execution fields actually exposed by the genuine public contract. Do not invent absent fields or a private receipt. A later different operation cannot overwrite the earlier unknown record. A selection change, local disposal, successful HTTP read, stable host label or new connection does not settle original durable uncertainty. Existing original task cancellation remains independently available and must not be swallowed by the worker unknown guard; cancellation does not imply instant stop, rollback or release of outstanding effects.

Only factual, exact correlated successful receipt/query facts can reconcile what they actually prove. A valid grant receipt does not prove create; a created idle worker does not prove execution; phase ready, a live connection or a catalogue response does not prove committed assistant input/output, capture, stop or settlement. An original WorkerManager query may report ready or unknown without any execution proof. An exact late operation receipt can record that operation's historical fact only if its public correlation/validation is available; it cannot restore current action authority, preaccept policy or continue the next operation. If required proof fields/methods are absent, retain UNKNOWN/HOLD rather than manufacture a query-success DTO with nonexistent semantics.
