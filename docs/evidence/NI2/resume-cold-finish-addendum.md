## Replay and uncertain orders

The normal wrapper checks current invocation, validates the closed request, then performs the scoped read **before** current-CAS, in-memory plan/map, native capability or session lookups. An exact authenticated historical match returns the unchanged original settlement receipt, even when later task/auth versions changed. A second guard check narrows the response; refusal after the read does not erase the committed settlement. It returns no new capability, context/prepared receipt, source-origin observation or resume eligibility beyond the already signed historical graph.

Same commandRef with changed request digest returns the existing core `IDEMPOTENCY_CONFLICT`, including old-versus-current CAS, action/claim/execution changes and cross-task reuse. A different command for an already-finished claim returns `WORKER_FINISH_UNAVAILABLE`; it creates no second receipt. A command present without the required normal association cannot be adopted. For a genuinely absent acknowledged association, first execution requires the existing current-CAS/private actual handle path; cold absence cannot stop/settle/release old unknown work. Native-stop-first but commit-not-acknowledged remains physical stop plus held/unknown accounting. No stop retry, inferred zero charge or automatic reconciliation effect is introduced.

In-memory exact duplicate may use this durable lookup too; its result must equal the existing immutable historical receipt. Storage/reopen/final-response failures preserve the committed receipt or original holds. Current source/config changes can deny new work while a permitted read still reports historical completion; they cannot reseal or upgrade old graph facts.
