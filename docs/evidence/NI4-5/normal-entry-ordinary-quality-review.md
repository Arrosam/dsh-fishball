## Source findings

**F1 — callback and return maps are exact in source; positive contract coverage is incomplete.** `createNormalAutomation()` supplies exactly 18 named installer callbacks and validates the six-key returned map. `createNormalResults()` supplies exactly 18 callbacks and validates the 17-key results return map, then checks the recipient adapter and optional notification data shape. The returned result map has 14 callable methods plus the three values `recipientAdapter`, `progressPolicy`, and `notifications`. This matches the proposal’s intended interface. NW01–NW11 do not directly assert all callback names/cardinality or reject a malformed installer map, so this remains source-established rather than fixture-established.

**F2 — local claim and permission use one original ledger facade; locked-call transaction behavior remains unverified.** In `installed-normal-services.mjs`, `pipelineStore` forwards pipeline reads and operations to the original `RuntimeStore` using the original owner/host handles. Its sole special claim slot calls `store.claimLocalDelivery(hostHandle, input)`; delivery publication and access likewise use original store methods. The composition creates the original `ResultPipeline` over that facade. Local permission calls `localAdmission(record)` and then `readLocalActionFacts({taskRef})`; that function reads current audit policy/native facts and calls the public `store.task()` and `store.getPolicy()` wrappers. Those public wrappers contain no public transaction-opening call in their bodies. The capsule comment says the read never opens a nested transaction. No permitted source fixture exercises this permission callback under the original claim lock, and this review does not inspect private transaction internals. Treat the locked transaction property as a residual verification boundary, not a demonstrated failure.

**F3 — event and schedule effects require explicit operations in the reviewed source.** Event construction creates deterministic slots but does not configure original source/subscription pairs. `configureLocalAutomation()` performs explicit source and subscription configuration; ingestion checks the current pair and calls original `ingestLocalOwnerEvent()`. Schedule polling starts only through `startLocalSchedule()` and original `ScheduleDriver.start()`; registration and start are explicit, and stop/disposal seal the token. Status computes a bounded proposed occurrence without making it an approval or cursor write. Runtime wiring constructs adapters but does not call configure, ingress, grant, dispatch, or schedule start automatically. NW02–NW04 provide source fixtures for explicit pair/ingress, stale-pair refusal, and stopped schedule restart; these fixtures remain unrun.

**F4 — nested result and notification response maps are closed in the latest source.** The client exact-checks the local preview description/data/model/environment/limits/charges and verifies bytes against the selected action’s data digest. It exact-checks nested artifact/publication status rows, the returned artifact/data/verification/verificationBinding maps, and notification candidates, batches, suppressed rows, and retry-required rows. NW09 covers extra status keys and a delayed byte read fenced by disconnect; NW11 covers extra nested artifact/data/suppressed fields while retaining usable readonly responses for original unreviewed artifact bytes and unverified progress suppression. Source review found the four artifact-summary states exact to `normalVerification()`; I retract the earlier suspected enum mismatch. These fixtures were not run.

**F5 — positive native result-to-local-publication and notification paths remain unproven by source fixtures.** NW05 verifies denial for unreviewed artifact bytes and unavailable native facts, with no action or delivery created. None of NW01–NW11 demonstrates an actual accepted native audit artifact proceeding through exact local preview, original grant, same-ledger claim, local publication, query, and current-access read. The fixtures also do not demonstrate notification policy/group claim and publication behavior. The wiring is source-composed, but this positive path awaits a fixture with genuine native facts and must not use synthetic verification as a substitute.

**F6 — uncertainty is preserved without mutation resend in the normal client source, but NI4/5 lacks delivery response-loss coverage.** `createNormalModel.run()` retains the original command and inputs in `uncertain` after a sent mutation fails, blocks subsequent mutations while uncertainty remains, and still allows readonly queries. The results adapter's `query()` reads the current same-ledger delivery projection; it does not call `send()`. `ResultPipeline.reconcile()` calls `adapter.query()` and never dispatches. NW07 covers lost acknowledgement and no resend for automation configuration; NW10 adds an actual source commit followed by disconnect and ignores a late acknowledgement. Neither fixture covers lost local publication acknowledgement, disconnect during delivery dispatch, or exact local-delivery query recovery. Thus the source path is read-only by inspection, while local delivery uncertainty behavior remains a coverage gap.

**F7 — third named observer is bounded and receipt-based in source.** The runtime accepts exactly one each of `producer`, `audit`, and `results`, with a size limit of three. `observe()` captures the original mutation receipt before synchronously notifying listeners; an asynchronous or throwing listener seals the installed runtime. This is a concrete source extension of the prior two-observer contract. Current fixtures do not exercise all three subscribers together, duplicate subscription rejection, or observer behavior for local plan/grant/policy/publication receipts.

**F8 — normal memory continuity uses actual adapter/store calls and named invalidation.** The composer passes the original owner store, coordinator projection, context assembler, and mutation observer into `createInstalledMemoryContinuity()`. Mutation handling validates returned metadata/receipt and invokes the runtime observer after the original mutation; runtime wiring clears protected contexts on those named mutations. NW06 source fixture reads an actual mutation receipt and command-history projection from the source classes. This is not a production memory/acceptance claim, and the fixture was not run.
