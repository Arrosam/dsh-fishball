# S35: what the agent sees after the plugin answers an approval (revision 11)

**Verdict: Pass with amendment.** All three questions pass on DSH 0.2.1-rc.2 and 0.2.1-rc.3, for direct calls and for calls made inside `run_code` (24 of 24 checks on each; the `run_code` part is section "PTC" below). The amendment is about mechanism, not behaviour: DSH's approval outcome can carry no text, so the wording is changed afterwards by a `tools/post-execute` listener, keyed by call id.

- Spike: [`spikes/s35-result-wording.mjs`](../s35-result-wording.mjs)
- Fixture: [`spikes/fixtures/s35-broker.mjs`](../fixtures/s35-broker.mjs)
- Evidence: [`S35-result-wording.json`](S35-result-wording.json) (rc.2) and [`S35-result-wording-rc3.json`](S35-result-wording-rc3.json) (rc.3). Run with `spikes/run.sh spikes/s35-result-wording.mjs`. For rc.3, also set `DSH_RUNTIME_ROOT=<rc.3>/node_modules S35_ID=S35-result-wording-rc3`.
- Setup: the harness boots the installed DSH in-process with the fake model. The "Fishball" in this spike is an ordinary session that the broker stand-in treats as Fishball. "Another plugin" is a separate host row with two tools:
  - `s35_other_gated`: a `tools/pre-execute` listener returns `ask` for it, as Auto review or a permission hook does.
  - `s35_other_body_ask`: its body calls `approval.request` and words the outcome itself, as sandbox escalation does.

## What DSH does on its own (rc.2 = rc.3)

- **No text in the outcome.** `ApprovalService.decide()` accepts only the four outcomes `allowed-once | rejected | cancelled | unavailable`. Any other value becomes `unavailable` (`dsh-user-approval/lib/index.js`, `decide`).
- **The fixed wording.** For a pre-execute `ask`, `ToolRuntime.serviceAsk` turns `rejected` into the denial `the user rejected tool "X"`, and the result text becomes `Error: <reason>` (`dsh-tools/lib/index.js:3535-3587, 3337-3350`). `serviceAsk` is identical in rc.3.
- **The hook point.** Every result passes through the `tools/post-execute` waterfall before it is committed, and denied calls are included: `prepareExecution` returns `post-result`, then `finalizeScheduledExecution` calls `postExecute` (`:3337`, `:3464`, `:3599`).
  - `{kind:'accept', content}` replaces the text and keeps `isError`.
  - `{kind:'block', feedback}` turns the result into an error whose text is `feedback`.
  - Either one may add `additionalContexts`.
  - Exactly the same text goes to the model and to the session log (checked for every call in the spike).
- **Tool-owned finalizers.** `dsh-tool-terminal` and `dsh-tool-jobs` run their `finalizeContent` after post-execute. Both only cut the text to a size limit, so the rewrite survives, though it can be shortened.

## Q1: hint on a managed session's direct call (item 12): Pass

**Mechanism.**
1. The broker's `approval/request` listener records `callId → {allow | reject, reason}` when it answers for Fishball.
2. A host-level `tools/post-execute` listener rewrites that call id's result once, then forgets the mark.

The agent sees exactly these texts:

| Case | DSH's own text (before) | Agent sees (after) |
|---|---|---|
| Allowed, pre-execute gate | `gated ran with allow-me` | `gated ran with allow-me` + `\n\nFishball approved this call once. Next time, call ask_fishball before a call that needs approval, and explain why it is needed.` (accept + content; `isError:false`) |
| Rejected, pre-execute gate | `Error: the user rejected tool "s35_other_gated"` | `Fishball rejected this call: deleting files outside the workspace is high risk\nNext time, call ask_fishball before a call that needs approval, and explain why it is needed.` (block; `isError:true`) |
| Rejected, the tool's body asks | `other plugin: approval rejected` | the same rejection text as the row above (block) |

Fishball's reject reason reaches the agent in full, and "the user rejected" no longer appears.

## Q2: Fishball's own call returns at once with "waiting" (item 21): Pass

**Mechanism.** When the asking agent is Fishball, the `approval/request` listener does three things:
- it files a card;
- it records `callId → card`;
- it answers `rejected` at once, so nothing waits.

How the text is then set depends on the kind of call:

| Kind | Who sets the text | Agent sees | Turn |
|---|---|---|---|
| Fishball's own tool whose body asks (`add_plugin` / `remove_plugin` / `set_plugin_enabled` stand-in) | The tool body asks `broker.cardFor(callId)` and returns the text as its value | `Waiting for your approval (card card_1). The call did not run. You will be told when the user answers; if they allow it, make the identical call again.` (`isError:false`) | 145 ms, idle |
| Another plugin's tool gated by a pre-execute `ask` (variant A: service, then a post-execute rewrite) | post-execute `block` over DSH's `Error: the user rejected tool "s35_other_gated"` | `Waiting for your approval (card card_2). …` (same sentence; `isError:true`) | 103 ms, idle |
| Same, variant B: a prepended `tools/pre-execute` listener calls `next()`, sees `ask` and returns `deny` itself | DSH's denial path | `Error: Waiting for your approval (card card_3). …` (DSH adds `Error: `; no `approval/asked` or `approval/decided` in Fishball's log) | 124 ms, idle |
| Another plugin's tool whose body asks | post-execute `block` over the body's `other plugin: approval rejected` | `Waiting for your approval (card card_4). …` (`isError:true`) | 123 ms, idle |

**Fishball keeps working.** After the `add_plugin` call returned, a second message to Fishball was handled in 64 ms with the card still pending.

## Q3: one-time pass for the identical retry (item 22): Pass

**Mechanism.**
- **Pass key.** The key is `sessionId | toolName | sha256(canonical JSON of the arguments)`. Canonical JSON sorts the keys.
- **Finding the arguments.** In the `approval/request` listener they are read from the asking session's log by `callId` (`argumentsOf`, as in `src/approvals.js`; spike S11). Variant B reads them from `exec.arguments` instead.
- **Allow.** The user's Allow stores the pass, and Fishball is woken with `[approval] The user allowed card card_1. Run s35_add_plugin again with the identical arguments.`
- **Retry.** A matching request consumes the pass and answers `allowed-once`. Anything else files a new card.

| Retry | Result |
|---|---|
| `add_plugin {spec:'pkg-a'}`, new call id, after Allow | `installed pkg-a` (ran) |
| `add_plugin {spec:'pkg-b'}` (different) | `Waiting … (card card_5)` |
| `add_plugin {spec:'pkg-a'}` again (pass already used) | `Waiting … (card card_6)` |
| gated `{spec:'x', flag:false}` after `{spec:'x', flag:true}` was allowed | `Waiting … (card card_7)` |
| gated `{flag:true, spec:'x'}` (same arguments, other key order) | `gated ran with x` (ran) |
| body-ask `{spec:'z'}` after Allow | `body-ask ran with z` (ran) |

## PTC: calls made inside `run_code`: Pass, with one difference

**Call ids match.** For every inner call, the approval request and the `tools/post-execute` exec carried the same call id, `<parent>:ptc:<n>` (for example `call_p_allow:ptc:1`). `argumentsOf` found the arguments in `tool/ptc-dispatch-start`, as in S11. Post-execute can tell an inner call from a direct one because `exec.parent` is set only for inner calls. No marks were left behind.

**The difference: an allowed inner call needs `additionalContexts`.** `run_code` hands the program the inner call's *value*, not its text (`dsh-tools/lib/index.js:1469`, `return outcome.value`). A content block appended in post-execute therefore never reaches the agent: the spike's first run showed only `gated ran with allow-me`. DSH does forward a nested result's `additionalContexts` to the outer `run_code` result (`:1458`, `exec.deferContext`). So for `exec.parent !== undefined` the listener returns `{kind:'accept', additionalContexts:[notice]}`. The agent then sees the `run_code` result, followed by a separate message whose source is `fishball-notice`: `Fishball approved this call once. Next time, call ask_fishball …`.

**Errors reach the program as thrown messages.** An error result (Fishball's reject, or a card) is thrown into the program as an `Error` whose message is the text post-execute set (`:1468`).

What the agent sees (identical on rc.2 and rc.3):

| Case (inside `run_code`) | Agent sees |
|---|---|
| Fishball allows, pre-execute gate | the result `gated ran with allow-me`, then a user-role context `Fishball approved this call once. Next time, call ask_fishball before a call that needs approval, and explain why it is needed.` |
| Fishball rejects, pre-execute gate | the program catches `Fishball rejected this call: deleting files outside the workspace is high risk\nNext time, call ask_fishball …` |
| Fishball rejects, the tool's body asks | the same rejection text |
| Fishball's request, pre-execute gate (program catches) | the program catches `Waiting for your approval (card card_8). The call did not run. …` |
| Fishball's request, program does not catch | `Error: code run failed (exception): ToolCallError: Waiting for your approval (card card_9). The call did not run. …` followed by a stack trace (`isError:true`) |
| Fishball's own body-asking tool | the value `Waiting for your approval (card card_10). …` (the body returns it) |
| Retry with different arguments after Allow | `Waiting … (card card_11)` |
| Identical retry after Allow (new inner id `call_pf_gated_retry:ptc:1`) | `gated ran with p` (ran under the pass) |

(The spike's catching wrapper prefixes caught errors with `THREW: `. Each turn took about 210-275 ms and ended idle.)

## Mechanism the build should use

1. **`approval/request` listener** (the existing `ApprovalBroker.#route`, prepended):
   - **Fishball's own requests:** look for a pass first (`allowed-once` when one matches). Otherwise file a Fishball card, record `callId → card`, and return `rejected` at once. Under policy `never`, DSH answers `rejected` before any listener runs, so no card is filed.
   - **Managed sessions:** after Fishball answers, record `callId → {allow, reason}` or `callId → {reject, reason}`.
2. **One host-level `tools/post-execute` listener**, the only place the wording is set for calls the plugin answered. For a recorded call id:
   - Fishball allowed it: `accept` with the hint appended to `content` for a direct call. For a `run_code` inner call (`exec.parent` set), use `additionalContexts` with a Fishball notice instead, because the program receives only the value;
   - Fishball rejected it: `block` with the reason and the hint;
   - it became a Fishball card: `block` with the waiting text;
   - it ran under a pass: `next()`.

   Delete the mark when it is used. The mark also needs a bound, or an end with the turn: a call that is cancelled may never reach post-execute after being asked.
3. **Fishball's own tool bodies** (`add_plugin`, `remove_plugin`, `set_plugin_enabled` in `src/plugin-tools.js`, which use `ask` there today): keep calling `approval.request`, so the request is audited and policy `never` is still honoured, then ask the broker for `cardFor(callId)`.
   - If there is a card, return a structured "waiting" result, for example `{ok:false, code:'waiting-for-approval', card}` plus the text.
   - Otherwise treat it as rejected, as today.
   - The body must not run its effect unless it receives `allowed-once`.
4. **The pass**: one-time and keyed exactly as in Q3. Its lifetime follows the requirements' defaults (used, withdrawn, or the end of the turn Fishball was woken for). Store it with the card so it survives a restart (item 24).

## Design amendments (for DESIGN §7a / N3)

- **N3.** Fishball's own requests no longer reach `next()` and the browser prompt. The broker answers `rejected` at once after filing a card. "What Fishball sees" changes from DSH's `the user rejected tool add_plugin` to the waiting text, set by the tool body (own tools) or by post-execute (other plugins).
- **The broker's code rule changes.** Today it reads "Fishball never answers its own requests → `next()`". It becomes "Fishball's own requests → card, or the pass of an identical earlier call that the user allowed". Code still never approves without the user's Allow.
- **Agent-visible wording** is a constant of the plugin (the texts above are a proposal), and it is applied in post-execute because `ApprovalOutcome` cannot carry text.

## Options for the user (not decided here)

- **Variant A or B for other plugins' pre-execute `ask` in Fishball's session.**
  - A (service, then post-execute rewrite): DSH audits the request (`approval/asked`, then `approval/decided: rejected`) in Fishball's log, and the agent sees exactly our text.
  - B (prepended pre-execute deny): the text carries DSH's `Error: ` prefix, and DSH records no `approval/*` events for it (the broker's own audit still has it). B does not cover body asks, so A is needed anyway.

  Recommendation: A only, so there is one path.
- **The `isError` flag of the waiting result.** `block` marks the result as an error (`isError:true`); an `accept` with replaced content keeps DSH's flag, which is also `true` for a denial. An own-tool body returns `isError:false`. Whether "waiting" should look like a failure to the model is a wording choice.
- **The hint on allowed calls.** Requirement 12 says "the agent's result then recommends ask_fishball". The spike appends it to a direct call's text, and sends it as `additionalContexts` for an inner call (the only way there). The build could also use `additionalContexts` for both, to have one path.

## Risks

- **Matching by call id.** The listener relies on `exec.callId` in post-execute equalling `req.callId` in the approval request. Checked for direct calls and for `run_code` inner calls (PTC section).
- **Uncaught inner errors.** When a program does not catch, `run_code` reports our text inside `code run failed (exception): ToolCallError: …` with a stack trace. The text is intact, but it is wrapped in DSH's wording, which the plugin cannot change. The model still sees "Waiting for your approval (card …)".
- **Finalizers.** A tool-owned `finalizeContent` (terminal, jobs) runs after post-execute and could shorten the text. Today these only cut text to their size limit.
- **What counts as identical.** The match is on the arguments as the model sent them, compared as canonical JSON. Two calls with the same meaning but different text (for example extra spaces in a command) do not match, and get a new card. That is the safe direction.
- **Marks left behind.** A call cancelled between the approval and post-execute leaves its mark behind. The mark needs a bound or a turn-end sweep.
- **Version drift.** DSH's wording `the user rejected tool "X"` is not relied on: the rewrite replaces it whatever it says. Only the post-execute contract is relied on, and it is the same in rc.2 and rc.3.
