## How it ran

- **Server:** `spikes/s37-client-slots-server.mjs` (port 3137; `SPIKE_PORT` overrides it). It boots the installed DSH in-process with the fake model, and links the fixture plugin `spikes/fixtures/client-slots` into a throwaway profile under `.runtime/`. Run it with:
  ```
  SPIKE_STDIN_SECONDS=7200 spikes/run.sh spikes/s37-client-slots-server.mjs
  ```
  It prints `S37-READY` with the URL and the session ids. For rc.3, add `DSH_RUNTIME_ROOT=.../0.2.1-rc.3/node_modules`.
- **Sessions:**
  - "Fishball", a stand-in for Fishball's own session;
  - "Docs" and "Parser", managed and frozen inside a real running `ask_fishball` call;
  - "Library", whose `ask_user_question` the fixture answered as Fishball;
  - "Plan", in plan mode, whose `exit_plan_mode` review the fixture approved as Fishball;
  - "Mine", the user's own session.

  Two more cards are fixture-only: a question card and a Fishball `add_plugin` card.
- **Fixture host half:**
  - the real `ask_fishball` tool. It waits on a promise that `POST /api/s37/answer` settles, and ends early on `exec.signal`;
  - a `user-questions/request` answerer, prepended, for the marked sessions;
  - `POST /api/s37/manage`;
  - `GET /api/s37/events` (server-sent snapshots).
- **Fixture browser half:** `spikes/fixtures/client-slots/client.js`. `window.__s37` records the props each slot entry received.
- **Browser:** the desktop app's browser pane (Chromium), with `prefers-color-scheme` emulated light and dark. Screenshots are in `spikes/results/S37/`, and the props and observations in `S37-client-slots.json`.

## 1. Allow once / Reject on the running `ask_fishball` row: Pass

- **What it does.** The keyed view renders while the call is in `phase: 'start'`, which is the whole time the session is frozen. It shows Allow once / Reject when Fishball's state stream holds a card with that call id.
  - Clicking Allow once posted the answer. The tool returned, and the row moved to `phase: 'result'`. The same card left Fishball's pile at once (4 → 3), so item 15 holds.
  - DSH's Stop on the frozen session aborted the call through `exec.signal`. The row settled "tool call aborted" and its card left the pile, so item 16 holds.
- **Extension point.** `ctx.slots.register({name: 'tool.call.toolview', key: 'ask_fishball'}, Row)`.
- **Props.** `callId`, `toolName`, `phase`, `block` and `sessionId`, with the standard hooks.
- **Arguments.** A started block keeps them in `block.argsRaw`. A settled result block keeps them in `block.call.argsRaw`.
- **The whole row is Fishball's.** DSH registers no view for `ask_fishball`, so a keyed hit replaces the generic card entirely. The build draws its own title, arguments and state with DSH primitives (`Button`, `Tag`, and `DisclosureRow` if it wants DSH's disclosure; there is no exported `ToolRow`).
- Screenshots: `ask-row-running-dark.jpg`, `ask-row-running-light.jpg`.

## 2. "Asked Fishball" tags: Pass with amendment

### Question rows: Pass

- **How it works.** An occupant of `tool.call.toolview`, key `ask_user_question`, at priority −1. It finds the next occupant (DSH's own question row, priority 0) through `ctx.slots.entries` and renders it unchanged, then adds the tag below it. This is the messenger's S25 pattern.
- The tag showed "Asked Fishball · date-fns (Recommended)" under DSH's "Ask question · 1/1 answered".
- **Visibility.** In a settled turn DSH folds tool rows under "Completed in …", then under the "Asked questions" group. So the tag shows only after the user expands both. While the turn runs, the row is in view.

### Plan-review rows: amended

`exit_plan_mode` has no keyed view in DSH. It renders through ui-tool's `GenericToolCard`, which is not exported, so no occupant can wrap it. Three placements were tried:

| Placement | Result |
|---|---|
| Shadow `conversation.chat.node` key `tool-call` at priority −1 and render DSH's tree inside | **Fail.** The occupant runs (name `exit_plan_mode`, call id, next occupant found), but its output never reaches the visible row; neither a fragment nor a wrapper element appeared in the DOM. Same on rc.3 |
| Fishball's own `tool.call.toolview` for `exit_plan_mode` | Works, but it replaces DSH's row in every session, because DSH has none to fall back to. Not recommended |
| `conversation.chat.turnTail` entry | **Pass.** The tag shows in the turn beside DSH's "Split the parser · Plan" card, visible without expanding anything |

**Amendment.** The plan-review tag goes in the turn tail, under that turn's plan card.

- A turn-tail entry receives `turn`, with `start.seq` and `end.seq`, but not the turn's call ids.
- So each tag the Host publishes must carry `{sessionId, callId, seq}`, where `seq` is the `tool/call` event's log position. The entry shows the tags whose `seq` lies inside the turn.

**A choice for the user, not made here: where the question tag goes.**

- **(a) On the question row** (as built). It sits next to what it answers, but in a settled turn it is hidden until the user expands the turn and its group.
- **(b) In the turn tail for both kinds.** Both tags are always visible and look the same, but they sit after the reply, not next to the question.

Both meet item 27's "a tag in the session's chat".

### Host-side findings for S36

- An untimed `ask_user_question` reaches `user-questions/request` with no `wait.callId`. The fixture supplied the call id itself; S36 must say how the build finds it.
- A plan review names its call in the intent: `{kind: 'plan-review', approve: 'Approve', callId}`.
- Plan mode is mounted per agent preset, so `ctx.planMode` is not on the root context. The fixture entered plan mode with `ctx.commands.execute(agent, '/plan', [], signal)`.

## 3. The pile above Fishball's composer: Pass

- **Extension point.** `conversation.input.dock`: a list in session scope, documented as "Full-width entries above the composer card". DSH's Todo and Queue docks use it.
  - The entry receives `sessionId`, `session` and the standard hooks.
  - It renders only when `sessionId` is Fishball's.
- **Live updates.** The entry reads a server-sent stream, as `client.js` already does.
  - The stand-in session showed "Waiting for you **4**": two live permission cards, a question card and a Fishball `add_plugin` card.
  - The count dropped when a card was answered in its own session, and when that session was stopped.
- **Each card shows:**
  - the session, a kind tag, the tool and the exact arguments;
  - the reason and Fishball's note;
  - a Details toggle that opens the quoted user messages and the discussion thread;
  - a note field and Allow once / Reject.
- **Height.** The stack is capped (45vh in the fixture) and scrolls, so the composer stays in view at 800×600.
- Screenshots: `pile-dark.jpg`, `pile-details-dark.jpg`, `pile-details-light.jpg`, `pile-dark-rc3.jpg`.

## 4. Hand over / Take back: Pass

- **Extension points.** The same two slots `client.js` uses for Send to Fishball: `sidebar.workspaces.session.menu.item` (props `sessionId`, `displayTitle`, `useMenuOpenState`) and `conversation.session.header.actions` (`sessionId`).
- **The user's session.** It showed "Hand over to Fishball" in both places. A click posted `{managed: true}`, and both switched to "Take back from Fishball".

## Design amendments to record (DESIGN §10, revision 11)

1. **The `ask_fishball` row** is a `tool.call.toolview` entry for key `ask_fishball`. It is Fishball's own row, since DSH has no row to wrap.
   - It shows Allow once / Reject while `phase === 'start'` and Fishball's snapshot holds a card for that `callId`.
   - It posts to a Fishball route.
   - It reads arguments from `block.argsRaw` (start) or `block.call.argsRaw` (result).
2. **The question tag** wraps DSH's row: a keyed entry at priority −1 that renders the next occupant. If the user picks option (b) above, it moves to the turn tail instead.
3. **The plan-review tag** is a `conversation.chat.turnTail` entry.
   - The Host's tag records carry `{sessionId, callId, seq, answer, kind}`.
   - The entry shows the tags whose `seq` falls between the turn's `start.seq` and `end.seq`.
4. **The pile** is a `conversation.input.dock` entry, rendered only for Fishball's session and fed by the state stream. Its height is capped and it scrolls.
5. **Hand over / Take back** sit beside Send to Fishball in the same two slots.

## Risks

- **Keyed lookup.** Wrapping DSH's question row relies on `ctx.slots.entries()` and on DSH's entry staying at the default priority, as the messenger already does.
  - If DSH changes its slot keys or priorities, the tag disappears or DSH's row is hidden.
  - The live check in each phase catches this.
- **Folded rows.** On question rows the tag is hidden inside the folded turn until the user expands it (see the choice above).
- **Turn-tail placement** depends on the `turn.start.seq` / `turn.end.seq` shape and on the Host recording the call's `seq`.
- **The `ask_fishball` row replaces DSH's generic card.** Inspect, file links and the failure styling are Fishball's to draw.
  - DSH's Auto-review denial still takes precedence over keyed views, so a denied `ask_fishball` shows DSH's generic row.
- **Dock order.** Not checked: the order relative to DSH's own Queue and Todo docks when they show at the same time (the fixture used `order: -100`).
- **The Messenger look's stylesheet** is scoped to Fishball's session and leaves the dock alone. The pile is styled from DSH's theme tokens and needs no messenger rule; not checked with the messenger on.
- **The 🐟 in the fixture tag** is a placeholder. The build uses FishMark.
- **Harness side effects (not product issues).**
  - Sessions the spike created in-process were listed under "Ungrouped", not under the "Work" workspace: the registry counted 0 members.
  - DSH's changed-files card picked up the evidence screenshots, because the spike's workspace sits inside the repo.
