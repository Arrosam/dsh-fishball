# S33: answering DSH's stock permission prompt from the server

**Verdict: Pass with amendment.** The plugin can answer a stock prompt that is already showing (Allow once or Reject). The prompt closes in the browser and the agent continues with the plugin's outcome. When the user clicks first, the plugin learns the user's outcome. The amendment: the idea as briefed ("call `next()` with a copy whose signal we control") does not work, because Cordis's `next()` takes no arguments. The listener must instead **re-dispatch the waterfall with a marked copy** (recommended) or **replace `req.signal` on the request** before calling `next()`.

Run 2026-11-01. Headless on 0.2.1-rc.2 and 0.2.1-rc.3, then in the Claude desktop browser pane against rc.2. The five DSH files involved are byte-identical in rc.2 and rc.3.

## Question

When DSH's stock permission prompt is showing in a session's browser, can the plugin answer it from the server so the prompt closes and the agent continues with the plugin's outcome? In reverse, when the user answers the stock prompt first, does the plugin learn the outcome, so it can clear its own card? This serves requirements items 15 and 20.

## How it works (host code read and confirmed)

1. **Waterfall.** `ApprovalService.decide` calls `ctx.waterfall(scopeTarget(agent, agent), 'approval/request', req, fallback)` (`dsh-user-approval/lib/index.js:176`). It captures `req.signal` locally first, so the service races only the asker's own signal.
2. **Cordis's `next()` ignores arguments.** `waterfall()` builds `next = () => (cbs.shift() ?? inner)(...args)` over the original argument array (`cordis/lib/index.js:317-324`). So `next(copy)` would still pass the original request. Listeners are bound to the scope target (`dispatch`, `hook.callback.bind(thisArg)`).
3. **Forwarder.** `dsh-api-remotes` `forwardWaterfall` hands the gateway the request object it received, then waits on `settled.promise` (`dsh-api-remotes/lib/index.js:233-249`). It requires `request.agent` to be the carrier agent (`carrierKeyOf(this)`).
4. **Gateway.** `startRemoteEvent` reads `request.signal` (`projectRemoteEventRequest`). On abort, `cancelRemoteEvent` removes the pending event, pushes `{type: 'cancel', eventId}` to every browser it was delivered to, and rejects the forwarder with the abort reason (`dsh-api-gateway/lib/index.js:1062-1140`).
5. **Browser.** The client's projected `request.signal` aborts on that cancel. `PendingApproval` calls `this.abort(reason)`, and the composer prompt disappears (`dsh-client-ui-approval/lib/client.js:191-201`).
6. **First answer wins.** Everything runs on one thread. `cancelRemoteEvent` and `receiveRemoteEventResult` both check `pendingRemoteEvents.get(id)`, so whichever arrives second is ignored. A browser result after our cancel finds nothing pending. A server answer after the user's click finds the fixture entry already settled, and the plugin refuses it.
7. **What `next()` does after our abort.** It rejects with our abort reason, never hangs, and is caught. The listener has already returned the plugin's outcome through `Promise.race`. If the user answers first, `next()` resolves with `allowed-once` or `rejected`, and aborting our controller later does nothing (the gateway already released its listener).

**Choices in the stock prompt.** There are two buttons, Reject (`rejected`) and Allow once (`allowed-once`). There is no "always" option. The client can also `delegate()` (hand the request to the next listener), but no button does that. DSH's outcome vocabulary is `allowed-once | rejected | cancelled | unavailable`, and any other value becomes `unavailable`.

## Mechanism the build should use

In `ApprovalBroker` (`src/approvals.js`):

- **Listener form.** Register with a `function` so the scope target is available: `ctx.on('approval/request', function (req, next) { return broker.route(this, req, next) }, { prepend: true })`. The current arrow function loses `this`.
- **Pass-through.** Replace every `next()` that hands a request to the stock prompt (escalate, timeout, not managed, cap reached) with `#passOn(target, req, next)`:
  ```js
  const own = new AbortController()
  const copy = { ...req, signal: req.signal ? AbortSignal.any([req.signal, own.signal]) : own.signal }
  passing.add(copy)                  // WeakSet: our listener calls next() for it at once
  const downstream = Promise.resolve().then(() => ctx.waterfall(target, 'approval/request', copy, () => 'unavailable'))
  // register { key, sessionId: rootSessionOf(...), toolName, callId, args: argumentsOf(...), at, answer(outcome) }
  // answer(outcome): if not settled -> settled; own.abort(); resolve the race with outcome
  return Promise.race([pluginAnswer, downstream.then(learn, () => settledOutcome)])
  ```
  `learn` runs when the user clicks first: it clears the card and the registry entry. The rejection after our own abort is expected and is swallowed.
- **Registry.** Keep the entry in a `Map` while the request waits. Remove it on any settle, including the asker's own `req.signal` abort (a stopped turn) and the cap. This is the data for `list_frozen_sessions`. It costs one Map entry and a log scan for the arguments that the broker already does, and it wakes nobody. Entries for the user's own sessions stay in process and reach Fishball only when it calls `list_frozen_sessions` (item 3).
- **Answering.** `answer_prompt` and the pile's Allow once / Reject buttons call the entry's `answer(outcome)` with `allowed-once` or `rejected` only. The return value says whether it won; a late answer gets "already answered".
- **No browser open.** The plugin's answer also settles a request the gateway is holding with no browser connected (headless: `gatewayPending` 1 → 0). Pile answers therefore work when the session's tab is closed.

Alternative, equally proven: **mutate.** Set `req.signal = AbortSignal.any([original, own.signal])`, then call `next()`. Both askers pass fresh object literals (`dsh-tools/lib/index.js:3551`, `dsh-sandbox/lib/index.js:105`), and the service has already captured the original signal. It is a single pass, but it writes to a request the service documents as "borrowed readonly". It would also break if DSH ever froze the request (the fixture catches that case and logs `mutate-failed`). I recommend re-dispatch for that reason. The mode is a technical choice that doesn't need the user.

## Design amendment (for DESIGN §7a and the S33 row)

- Strike "DSH cannot withdraw a browser prompt once it is shown, so the assistant never answers a request after escalating it." A plugin-owned abort signal on the forwarded request withdraws it. The broker can answer after escalating, and the first answer wins.
- The broker re-dispatches the waterfall with a marked copy instead of calling `next()` directly. "Escalate" then means "show the stock prompt **and** a pile card", and either one can answer (item 15).
- `answer_prompt` / `list_frozen_sessions` (item 20) read the broker's pass-through registry. They don't need any other DSH API.

## Risks

- **Listeners prepended after the broker run twice.** In re-dispatch mode, a listener that sits in front of the broker sees the original and then the copy. The headless run counted three `approval/request` listeners: the fixture, the stand-in and the forwarder. `dsh-acp` and `dsh-api-remotes` register without `prepend`, so they sit behind the broker. A future prepended answerer that returns a value on its first pass would answer before the copy is made, which is harmless. One that only observes would log twice.
- **Reliance on host internals.** The design relies on the gateway honouring `request.signal` for forwarded waterfalls. That is documented in `projectRemoteEventRequest` ("the optional Host cancellation signal") and in the client's `PendingApproval`. It is not a published plugin contract. A DSH change there would leave the prompt open after a pile answer. The tool would still get the plugin's outcome, because the race returns it, but the browser would show a stale prompt until the user clicks, and that click would be ignored.
- **Race fairness.** On loopback the server answer always reached the Host before the browser's click (the click goes through React state and an HTTP POST). Either way only one answer counts, and the losing side sees the request disappear: the browser via the cancel frame, the plugin via "already answered".
- **Not tested with two browser tabs on one session.** Code reading says `finishRemoteEvent` sends the cancel frame to every client the request was delivered to.
- **Reject note.** The user's optional Reject note (requirements Defaults) cannot travel in the outcome. DSH words a rejection itself ("the user rejected tool X"). Getting the note to the agent belongs to S35.
- **Audit and attribution.** `approval/decided` in the session log records only the outcome, not who answered. Whether a plugin-answered prompt gets a tag in the session is the open question already listed in the requirements.
