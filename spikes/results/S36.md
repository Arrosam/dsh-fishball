# S36: routing `ask_user_question` and plan reviews to Fishball (server side)

**Verdict: Pass with amendment.** Run 2026-11-01 on rc.2 and rc.3. All 16 checks passed on both: 12 in the main phase, 4 after a restart.

- **Mechanism:** a prepended, host-level `user-questions/request` waterfall listener. It replaces `request.signal` with one it can also abort, then calls `next()` straight away, so the session's own question card opens as usual. Fishball's answer and the browser's answer race, and the first one wins.
- **Continued questions** are answered with `ctx.userQuestions.answer(agent, callId, batch)`, the same method the browser's RPC calls.
- **Amendments:** restart behaviour, the legacy call id, and plan-review feedback (see below). Two choices are left for the user.

Browser checks (tags and buttons) are S37's job. Here the browser is a stand-in connected to DSH's real typert gateway as an owner client, so forwarded requests, `cancel` frames and answers go through the real Host path. Only the websocket is skipped.

## Questions and verdicts

### Q1. Can a plugin intercept a chosen session's question and answer it in the browser's exact shape, for every kind? **Pass, amended (legacy call id).**

**How it worked.**
- `ctx.userQuestions.ask()` dispatches `user-questions/request` with `scopeTarget(agent, agent)`. A host-level listener registered with `ctx.on(…, {prepend: true})` runs before `dsh-api-remotes`' forwarder, as with approvals in S12.
- An unmanaged session's request went straight to `next()`, and the router created no entry (case C).
- The test batch had five questions: single-select, multi-select with custom text, free text, custom text that replaces a single-select choice, and a skipped question.
- Fishball's batch from `composeAnswer` was deep-equal to the browser's `submitDrafts` batch. The tool result text was byte-identical in every case:
  - Fishball answered (A);
  - the browser answered (B);
  - an unmanaged session (C);
  - timed mode with Fishball answering inside the window (F1):
  ```
  {"answers":[{"id":"color","selected":["Blue"]},{"id":"parts","selected":["Docs","Code"],"custom":"and CI"},{"id":"name","selected":[],"custom":"fix/s36"},{"id":"size","selected":[],"custom":"XL"},{"id":"skip","selected":[]}]}
  ```
- Bad batches were refused before reaching DSH, and the question stayed open:
  - a missing item (`one item per question`);
  - two labels on a single-select question.

**Continued questions** (timed mode only, see Q4):
- The browser's countdown ended with `ASK_TIMED_OUT` (F2), or no browser was open and the Host's own timer fired (F4). Either way the tool returned `{"pending":true,…}` and the projection showed the call as `continued`.
- Fishball's `answer` then went through `userQuestions.answer` and steered one `user-question-reply` message, `{kind:'answer_to_pending_question', …, answers}`.
- The model saw that message on its next request.
- The projection then listed the call under `settled`, with the answers.
- A later browser answer returned `false`.

**Amendment: legacy questions name no call.**
- The shipped presets use the blocking legacy tool, which sends no `wait`. Its request therefore has no `callId`. Timed calls carry `wait.callId`, and plan reviews carry `intent.callId`.
- The router recovers the id from the session log: the `ask_user_question` `tool/call` that has no `tool/result` yet and whose question ids match the request (`callIdFromLog`). Case A found `call_a` this way.
- The build needs this for the "Asked Fishball" tag (S37 needs a callId) and for the audit.

### Q2. Can the session's own card stay open at the same time, with the first answer winning? Does Fishball learn when the user answers first? **Pass.**

**Fishball answers first** (A, F1, P1, P2):
- The router aborts its own signal.
- The gateway's `cancelRemoteEvent` sends `cancel` to every owner client. The stand-in recorded `closed: 'cancel'`, and `pendingRemoteEvents` was empty.
- The forwarder's `next()` then rejects, and the router ignores that rejection.

**User answers in the session first:**
- Open question (B): `next()` resolves with the browser's batch. The router records `by: user` with that exact batch, and Fishball's later answer gets `already-settled`.
- Continued question (F3): the browser's RPC body steers the reply. The router learns the answer from the `user/message` session event whose source is `user-question-reply` with that `callId`, parsing the answers from its text. Fishball's later answer gets `already-settled`.

**Turn stopped while the question is open** (E):
- The original signal aborts, so the browser gets `cancel`.
- The router closes its entry, and Fishball's answer is refused.
- The tool result is `ASK_ABORTED`.

S34's note agrees: `sessionController.cancel` aborts `req.signal`.

**Why replacing the signal works:**
- Cordis' `waterfall` gives every listener the same argument array, and `next()` takes no arguments (`cordis/lib/index.js` `waterfall`).
- The gateway reads `request.signal` only when the forwarded event starts (`startRemoteEvent`).
- `ask()` builds a fresh `{...request, agent}` for the waterfall, so the change does not leak back to the caller.
- The request must stay plain JSON apart from `agent` and `signal`. Otherwise `projectRemoteEventRequest` refuses it, so put no marker fields on the request.
- S33 reached the same gateway path for approvals by re-dispatching a copy with `ctx.waterfall(this, …)` and a WeakSet marker. Either works. The build should use one mechanism for both brokers: replacing the signal is fewer lines; re-dispatching does not depend on `ask()` copying the request.

**How the browser reacts to `cancel`** (read from `dsh-client-ui-user-questions`, not exercised in a real browser here):
- The card's channel ends with `ASK_ABORTED`.
- A legacy card has no `callId`, so it is removed at once.
- A timed card is keyed by `callId`. It is removed when the projection settles, which happens as soon as Fishball's answer becomes the tool result.

### Q3. The same for plan review (`exit_plan_mode`): approve, and reject with feedback. **Pass, amended (feedback shape).**

**The request.** A plan review is a blocking `ask()`: no `wait`, one question `plan-review` with `intent: {kind: 'plan-review', approve: 'Approve', callId}` and `detail` = the plan.

**Approve** (P1):
- Fishball's batch is `{answers:[{id:'plan-review', selected:['Approve']}]}`, deep-equal to what the browser's `PlanReviewPanel` `decide()` sends.
- The tool result was the same as when the browser approved (P3): "Plan approved — plan mode exited; …".
- `/plan off` afterwards answered "Plan mode is already inactive."

**Reject with feedback** (P2):
- `planDecision(question, {approve: false, feedback})` gives `{id, selected: [], custom: feedback}`. This is the generic card's shape for typed text, and it is deep-equal to `submitDrafts`.
- `dsh-plan-mode` turned it into the tool error "The user chose to keep planning; their feedback: Add a restart test first."
- Plan mode stayed on: `/plan off` answered "Plan mode off."
- Rejecting with no feedback sends `selected: ['Keep planning']`.

**Amendment.** In rc.2 and rc.3 the session's plan-review panel has only **Approve** and **Discuss**, with no feedback field.
- **Discuss** rejects with `ASK_CANCELLED`. `exit_plan_mode` then ends the turn and returns "The user dismissed the plan review…" (P4). The router saw this as `closed:ASK_CANCELLED`.
- So "Keep planning, with feedback" exists only through Fishball or the pile card, not in the session's own card. The pile card can offer Approve and Keep planning with a text field, in the same shape.
- A user's Discuss in the session closes the pile card: the router learns of it.

**User first** (P3): the router learnt `selected:['Approve']`, and Fishball's later answer was refused.

### Q4. What happens to an intercepted question across a DSH restart? **Pass, amended: depends on the tool mode.**

Restart phase: the same home booted again, the managed sessions resumed with `resolveAgent`, and `router.recover(agent)` read the `userQuestions` projection.

| Left open at quit | After restart |
|---|---|
| Legacy (blocking) question, the shipped default | Ended. Resume repair wrote "The tool call was interrupted… outcome is unknown". Not in the projection. The router recovered nothing |
| Plan review (always blocking) | Ended, the same way. Plan mode stays on |
| Timed question still in its foreground window | `continued`: the repair's `TOOL_OUTCOME_UNKNOWN` result counts as pending. Recovered |
| Timed question already continued | Still `continued`. Recovered |

- No waterfall was replayed to the browser, because no tool call is running any more. DSH's own session card for a continued question is drawn from the projection.
- Fishball answered the recovered `call_rt` through `userQuestions.answer`. The reply was steered, its answers matched, and the model saw it in a new turn.
- An ended legacy question or plan review leaves the agent idle, with the "outcome unknown" result, until the next message.

**Amendment:** requirements item 16 ("session cards do not survive a restart") holds for blocking questions and plan reviews only. Timed-mode questions survive in DSH. If their pile cards should survive too, the router can rebuild them from the projection on boot (this is a choice; see below). Restart needs no other code: open waterfalls end with their process.

### Q5. Questions from live child agents. **Pass: nothing reaches Fishball, and nothing should.**

- `ask()` runs `assertLiveRoot` before the waterfall, and a child owned by a live parent gets `DELEGATED_CALLER`: "human interaction is unavailable while the calling agent is owned by another live agent; include the unresolved question or decision in the child agent's final result".
- Case K: a managed parent started a `subagent`, and the child called `ask_user_question`. The router saw 0 requests, and the child's tool result was that error.
- This matches the requirements' non-goal ("no special rules for subagents"). The child's unresolved question reaches its parent in the child's result. If the parent then asks, its question is routed as usual.
- Plan reviews go through the same `ask()`, so a child cannot hold one either.

## Mechanism the build should use

1. **Registration.** In the `fishball` row (the RequestDesk in rev11-design's §3), add one listener: `ctx.on('user-questions/request', listener, {prepend: true})`. It must be prepended after DSH's rows load, which the row position gives, as for the ApprovalBroker.
2. **Routing.**
   - `next()` without an entry when the request has no `agent`, the session is not managed, Fishball is unavailable, or the Questions plugin is off. That last case answers Q-r11-question-off as proposed: the question stays in its session.
   - Otherwise mint `qst_<id>`. Take the `callId` from `wait.callId`, then `intent.callId`, then `callIdFromLog`. The kind is `plan-review` when `intent.kind === 'plan-review'`. Record `timed = wait.timed === true`.
   - Then replace `request.signal` with `AbortSignal.any([original, own])` (or re-dispatch as S33 did) and call `next()` straight away.
3. **The race.** Take the first of:
   - **Fishball's answer:** `own.abort()`, then return Fishball's batch.
   - **`next()` resolving:** the user answered in the session. Record it, clear the pile card, and tell Fishball without waking it.
   - **`next()` rejecting:** `ASK_TIMED_OUT` on a timed question → `continued`; anything else (stop, Discuss `ASK_CANCELLED`, abort) → closed, and the card leaves the pile. Re-throw in both cases so DSH maps the outcome itself.

   Decide the winner synchronously in one place (a settled flag), so two answers in the same tick cannot both count.
4. **Fishball's tool** (working name `answer_question`).
   - It takes `{question_id, answers: [{id, selected, custom?}]}`, or `{question_id, approve: true}` / `{question_id, feedback}` for plan reviews.
   - Validate it with `invalidAnswer`: each id exactly once; selected labels must be offered options; a single-select question takes one label, or custom text alone. Build the batch with `composeAnswer` / `planDecision`.
   - Open question: resolve the race. Continued: `ctx.userQuestions.answer(liveRootAgent, callId, batch)`, after `sessionController.agents.resolveAgent(sessionId)`. A `false` result or `REPLY_QUEUED` means the user answered first, so answer `already-settled`.
5. **Learning continued answers.** Use a global `session/event` listener on `user/message` with `source.kind === 'user-question-reply'`, and ignore the reply Fishball is sending at that moment.
6. **On boot.** For each managed session, read `sessionProjections.stateOf(session, 'userQuestions').questions.active` with `state === 'continued'`, if the user wants those cards to survive (choice 2).
7. **Audit.** Record every Fishball answer: session, `callId`, kind, batch digest, and which side won.

## Design amendments for DESIGN.md (owner: rev11-design session)

- **§7a "`ask_user_question` always stays with the user"** becomes: for managed sessions, the router above, and the session card stays open in parallel. This change is already approved.
- **Legacy questions carry no `callId`.** The router recovers it from the log (Q1).
- **Plan-review feedback** exists only through Fishball and the pile card. The session panel offers Approve and Discuss, and Discuss ends the turn (Q3).
- **Restart:** blocking questions and plan reviews end at a restart. Timed questions survive as `continued` and can be answered by Fishball or in the session (Q4). Item 16 needs this qualification.
- **Children:** nothing to build (Q5).

## Choices for the user (not decided here)

1. **When the session's own card appears for a managed session's question.**
   - **(a) At once** (what the spike built and checked). The user can answer in the session while Fishball decides, and the first answer wins. Timed questions keep DSH's browser countdown.
   - **(b) Only once Fishball gives up** (its 120 s, or a hand-off to the pile). The session shows no card until then, so the router calls `next()` late. A timed question would hit the Host's unattended timer unless the router holds the wait with `userQuestions.attachWait(agent, callId, signal)` while Fishball decides. The service allows any holder; not exercised here.

   Item 26 ("the user can also answer them in the session's own question card") reads like (a). In User mode the two are the same.
2. **Pile cards for continued timed questions across a restart.** Rebuild them from the projection (they stay answerable in DSH anyway), or let them leave the pile, as item 16 says for session cards. This applies only if timed mode is used; the shipped presets are legacy.
3. **Timed mode and Fishball's 120 s.** In timed mode the tool's own `timeout` (default 120 s, set per call by the model) can end the foreground wait before Fishball answers. Fishball's later answer then arrives as a `user-question-reply`, which starts a new turn in that session. Accept this, or have the router hold the wait (see 1b) until Fishball's own limit.

## Risks

- **Signal replacement** relies on `ask()` passing a fresh, JSON-only request object (rc.2/rc.3 `{...request, agent}`). A DSH change there would break it. S33's re-dispatch is the fallback.
- **The legacy call id** is inferred. Two parallel `ask_user_question` calls with the same question ids are ambiguous (the newest is taken). The tag (S37) then might attach to the wrong row.
- **A continued answer from Fishball wakes the session** and starts a turn, which costs that session a step. This is DSH's own behaviour for late replies.
- **`userQuestions.answer` needs the live root agent.** Answering a closed session resumes it, as the browser's RPC does.
- **Not exercised here:** the visible closing of the browser card was read from client code; S33 (approvals) and S37 cover it in a real browser. Also not exercised: `run_code` inner calls (PTC), which enter the projection only when their result is pending.
