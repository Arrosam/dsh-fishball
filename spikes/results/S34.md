## Q1: tools only in managed sessions

### Evidence

There are two live ordinary sessions, A and B. The fake model records each request's `tools`.

DSH's session-title request reuses the session id and sends no tools, so only agent-loop requests (those with tools) are counted.

| Check | Result |
|---|---|
| Before connect | Neither A nor B has any of `ask_fishball`, `message_fishball`, `list_user_messages` |
| After `connect(A)` | A's next request has all three. B's has none, and neither do B's registry view or the global view |
| A calls `ask_fishball` | Runs (`ask_fishball ran`) |
| B calls `ask_fishball` | `Error: unknown tool "ask_fishball"` (`UNKNOWN_TOOL`); the tool body never runs |
| After `disconnect(A)` | A's next request has none of them, and A's call is refused with `UNKNOWN_TOOL`. The fixture's call log shows only the one call from A |
| Mid-turn | A tool in step 1 connects its own session. Step 1's request has no managed tools; step 2's request in the **same turn** has all three |
| Re-created agent | A session connected, its agent disposed, then `ctx.agents.resume` again: the new agent has the tools, through `agent/created` |
| Fishball's plugin stops (owner "plugin") | Tools are gone from the session |
| Fishball's plugin stops (owner "agent") | Tools **stay** in the session (a leak) |
| Alternative: global tool + `agent.ctx.tools.restrict({deny})` on a live agent | Also toggles live, per session (denied → hidden in that session only; lifted → visible) |

### Mechanism for the build

1. **Do not register the managed tools globally.** Today `message_fishball` is a host-row global tool hidden only from Fishball (Q-exposure). Register `ask_fishball`, `message_fishball` and `list_user_messages` per managed agent instead:
   ```js
   const scope = createScope(fishballRowCtx, scopeOf(agent.ctx))   // dsh-scope
   const undo = TOOLS.map((t) => scope.ctx.tools.register(t))       // sync disposers
   // take back: undo.forEach((d) => d()); scope.dispose()
   ```
   - This lands in the agent's own scope layer (`ScopedLayers` keys layers by scope key), so only that agent sees the tools.
   - The context is owned by Fishball's plugin fiber, so turning Fishball off, or reloading it, removes them everywhere.
   - `agent.ctx.tools.register` also works, but its registration belongs to the agent's fiber and outlived the plugin in this spike.
2. **Remove synchronously.** `scope.dispose()` is async (`quiesceFiber`). In the first run, a request assembled before it settled still listed the tools; the call was still refused, because execution resolves visibility again. Call each `register()` disposer first: they undo synchronously.
3. **Re-apply on every new agent.** Listen with `ctx.on('agent/created', ({agent}) => …)` on Fishball's host row (unscoped, so it sees every agent). Apply the tools when `agent.id` is managed. DSH creates a new agent on resume, clear and compaction (`SessionStartSource`), and scoped registrations end with the old one. Also drop the entry on `agent/disposed`.
4. **Connect and disconnect** are `managed.add(id)` plus applying the tools to the live agent (`ctx.agents.get(id)`), and the reverse. They take effect at the session's next model request, including the next step of a running turn. The registry's `view()` is recomputed on every `schemas()`, `get()` and dispatch; there is no per-turn tool snapshot.
5. **Refusal is DSH's own.** A call to a tool the session cannot see returns `UNKNOWN_TOOL` before any body runs. No guard is needed for a non-managed session. A guard is still worth keeping for Fishball's own session, as today.
6. **System prompt text** must follow the same rule (item 3: nothing in a user's session mentions Fishball). The system-prompt registry is scope-aware (DESIGN §2 "Scoped registration"), so any section the managed tools need goes through the same scoped context. This spike did not exercise prompt sections.

### Design amendment (DESIGN §5b, Q-exposure)

- `message_fishball` stops being a host-row global tool. All three tools are per-agent scoped registrations made while a session is managed.
- The ~150-token cost now applies only to managed sessions.
- §5b's "masked for Fishball itself" becomes moot: Fishball's own session is never managed. The guard stays as defence.
- Revision 10c's "Session messages off takes `message_fishball` away from every session" becomes "takes it away from every managed session": disposing the per-agent registrations does this.

## Q2: stopping a running turn

### What the Stop button does

- The browser's Stop button (`dsh-client-ui-conversation` `stop(sessionId)` → `scopedConversation(...).cancel()`) calls the Remote method `session.cancel`.
- On the host this is `ApiSessionController.cancel({sessionId})`: `agent.cancel({ kind: 'user' }, { keepInbox: true })` (`dsh-api-session-controller/lib/index.js`, `cancel`). It refuses a session owned by a live parent agent (a subagent) and a session with no live agent (`session/not-found`).
- A plugin calls the same method in-process: `ctx.sessionController.cancel({ sessionId })`. That makes it the Stop button's code path by construction, not an imitation.

### Evidence

| Pending item | What happened after `sessionController.cancel` |
|---|---|
| **Approval request** (a `tools/pre-execute` ask; with no browser, DSH's gateway holds it pending, as a showing prompt) | `ack {accepted:true}`. The waterfall's `req.signal` went from not aborted to aborted (reason kind `user`). `approval/decided` = `cancelled`. The tool result is `Error: tool call aborted before dispatch` (`ABORTED_BEFORE_DISPATCH`). `turn/end` = `aborted`; the agent is idle, and the next scripted response never ran |
| **`ask_user_question`** (pending in the `user-questions/request` waterfall) | The request signal aborted. The tool result is `Error: ask_user_question was aborted before the user answered` (`ASK_ABORTED`). `turn/end` = `aborted`; idle. The `userQuestions` projection holds no active question afterwards |
| **Idle session** | `{accepted:true}` and a no-op: no turn end is written |

**For the build:**
- Fishball's own answerers (its `approval/request` and `user-questions/request` listeners, and its pile cards) should treat `req.signal` `abort` as "cancelled: remove the card". That signal fires on Stop, on `stop_session`, and on any other turn end.
- Whether the browser's own prompt closes on that signal is S33's question.
- The web preset's `ask_user_question` is the blocking schema, so a question never becomes `continued` (answerable after its turn) there. With the opt-in timed tool, a question that had already timed out to `continued` would **not** be cancelled by a stop. This spike did not test that; it matters only if a profile enables the timed tool.

## Q3: a new turn after the stop

### Evidence

| Check | Result |
|---|---|
| Stop, then `agent.followup(msg)` | One new turn starts, ends `completed`, and answers from the new script. Turn ends: `aborted`, `completed` |
| `redirect` = stop + an immediate `followup` | The new turn runs the redirect instruction. The old turn's approval is `cancelled` and the old script never continues. DSH queues waking input submitted during cancellation until the aborted turn has settled, so no `whenIdle()` wait is needed |
| A message the user queued before the stop (`keepInbox`) | **No turn starts.** The message stays parked in `inbox.nextTurn` until the next wake. So "stays idle until the next message" (item 28) holds |
| Redirect while such a parked message exists | Both run, in order: first the user's parked message, then the redirect instruction (first in, first out) |

### Option for the user (do not pick in the build)

Requirement 29 says redirect "stops the turn and sends the instruction as a new turn", but does not say what happens to messages the user already queued in that session:

- **A. First in, first out (DSH default, as tested).** `followup(msg)`. The user's queued messages run first, then Fishball's instruction. Nothing of the user's is lost, but the redirect is delayed by however long those turns take.
- **B. Redirect first.** `agent.inbox.prepend('next-turn', msg)` and then wake the agent (or `send(msg, 'next-turn', true)` after the prepend). Fishball's instruction runs next, then the user's queued messages. This was not run in this spike; it is a documented `Inbox` API.
- **C. Clear the queue.** `agent.cancel({kind:'user'})` without `keepInbox`. This discards the user's queued messages, unlike the Stop button. Not recommended, since it drops user input.

The same question applies to `stop_session`: with Stop-button semantics (A), the parked message runs at the session's next wake, which could be the user's next message or Fishball's.

## Subagents

| Setup | What the child agent's request had |
|---|---|
| Subagent (`subagent` tool) of a **managed** session, default fixture | **No** managed tools |
| Subagent of an unmanaged session | No managed tools |
| Opt-in fixture (`subagents: true`): `agent/created` walks the session header (`origin: 'subagent'`, `parentSession`) to the root, as `src/session-info.js rootSessionOf` does, and applies the tools when that root is managed | The child **has** all three |

- Subagents do not inherit their parent agent's scope layer, so they never see the parent's scoped tools unless Fishball applies them.
- This is a behaviour change: today a subagent can call the global `message_fishball`, and its message is attributed to the root session (§5b "As built").
- **User choice.** Requirements non-goal: "No special rules for subagents… one that gets through counts as its parent session's."
  - **(a) Children get no Fishball tools.** Simplest; nothing to build.
  - **(b) Children of a managed root also get them.** Apply on `agent/created` by root, and remove them from live children on take-back. Shown working above.
- Either way, Stop on a parent ends the parent's turn. Children are separate agents, and `sessionController.cancel` refuses a child session directly. This spike did not test what happens to a running background child when its parent stops.

## Risks

- **Ownership leak.** Registering through `agent.ctx` would outlive Fishball's plugin (shown). Use a plugin-owned context tagged with the agent's scope key.
- **Async scope disposal.** Always undo with the per-registration disposers before `scope.dispose()`.
- **`createScope` with another agent's key** is not a documented use: the key is "opaque identity used for listener routing". It works on rc.2 and rc.3 because `ScopedLayers` keys layers by scope key. If DSH ever makes scope keys exclusive, use the `agent.ctx` path with an explicit cleanup in Fishball's own `ctx.effect` disposer instead. That variant also toggles correctly; it only lacks automatic unwind.
- **`agent/created` source coverage.** Re-apply was tested for `resume`. `clear` and `compaction` use the same event (by its type), but were not exercised here.
- **Requests already being assembled** when a toggle happens see the old set. The next request sees the new one, and execution always re-checks.
- **Inspection noise.** DSH's session-title request shares the session id but carries no tools. Any evidence that reads "the session's last request" must skip it.
